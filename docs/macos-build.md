# Build Halo in AssaultCube on macOS

The engine source comes from AssaultCube Lockdown Edition v1.3.0.2, commit `1ece5af7533983bb8f827616381d282470793d90`. Engine and ENet notices are in `source/`. Stock data is read from a local AssaultCube RC1 release. The ten Halo missions, viewmodels, characters, compiled mission scripts, cinematic geometry and audio are generated from expanded Halo CE Xbox map caches. [AssaultCube v1.3.0.2](https://github.com/assaultcube/AC/tree/v1.3.0.2)

## Dependencies

Install Apple's command line tools, Python 3.9 or later, CMake, and the Homebrew formulae `sdl2-compat`, `sdl2_image`, `libvorbis` and `libogg`. The cinematic audio importer uses FFmpeg. The client uses the system OpenGL and OpenAL frameworks. `CMAKE_PREFIX_PATH` can point CMake at libraries outside the default Homebrew prefix.

```bash
brew install cmake sdl2-compat sdl2_image libvorbis libogg ffmpeg
```

Set `AC_ASSET_ARCHIVE` to the original `AssaultCube_v1.3.0.2_LockdownEdition_RC1.tar.bz2` file. The scripts also look for it in `~/Downloads`. The staging script checks its SHA-256, extracts game data and retains the bundled license in `build/runtime/docs/license.html`.

## Import, build and play

Run from the repository root with the directory that contains the expanded North American Xbox Halo CE 1.0 maps. Halo3DS's prepared `halo-source` directory has this layout. The campaign import needs all ten mission caches; the asset library also imports any multiplayer and menu caches in the same directory.

```bash
maps="/path/to/halo-source"
./scripts/import-macos-assets.sh "$maps"
./scripts/package-macos.sh
```

Open `build/Halo in AssaultCube.app` in Finder; it opens on the title menu (see Title menu and saved games). The app includes the staged data and converted files from `packages/`. `package-macos.sh` copies the non-system dylibs (SDL2, SDL2_image, Vorbis, Ogg and their dependencies) into `Contents/Frameworks`, rewrites their install names to `@executable_path/../Frameworks`, ad-hoc signs everything and fails if any `/opt/homebrew` path remains, so the app can be moved to another Apple Silicon Mac. It always verifies the full 55-section import (all `.cgz/.cfg/.mesh`, the `.hcol` files of the retail-collision missions, driven sections included, the ten `.hscb` and the weapon, equipment, actor and vehicle tables) and exits non-zero if anything is missing; pass `--partial` for a development package that only needs the Crash Site files, and set `HALO_PACKAGES_DIR` to package another asset directory. It also runs `scripts/check-no-retail.sh`, which fails if a retail-derived file is tracked, staged or not ignored (everything under `packages/` is ignored except `maps/halo_a30.cfg`), and refuses a `build/macos` configured with `HALO_SANITIZE=ON` (Robustness, sanitizers and CI). Licences ship in `Resources/licenses`; see `NOTICE.md`. Run `./scripts/build-macos.sh` and `./scripts/play-macos.sh` for source development. The campaign importer supports `--mission` and `--part` for focused map edits, writes each section's route metrics beside its map, and with `--metrics-only` writes only those (Route metrics). The script importer supports `--mission` and can regenerate the cinematic BSP meshes and models with `--rebuild`. Run `python3 tools/import_halo_scripts.py "$maps" --mission a10` before repackaging to upgrade an existing Autumn flyby mesh.

`build/retail-assets/catalog.json` indexes the local development library. It records every cache and tag, all BSPs, scenario placement tables, animation tracks, and looping sound definitions. The library copies the original caches into `sources/` and exports first-person and static models, full BSP meshes and collision, bitmap PNGs, and sound variants. Bitmap exports include cubemap faces and volume slices; P8 bump images preserve palette indices. WAV assets preserve the original Xbox sample encoding. The catalog records conversion gaps, and the copied caches retain the original data for future work. The campaign app uses its own converted media; the multiplayer caches and the original `ui.map` menu are in the library only (multiplayer and the retail menu are out of scope, NOTICE.md). Rerun only the library with `python3 tools/import_halo_library.py "$maps"`; add `--rebuild` to regenerate converted assets.

The Silent Cartographer uses retail collision across all three sections. To update an existing campaign install, regenerate the maps and script projections, then package the app.

```bash
python3 tools/import_halo_campaign.py "$maps" --mission b30
python3 tools/import_halo_scripts.py "$maps" --mission b30
./scripts/package-macos.sh
```

The original structure collision surfaces handle movement, weapon traces, and bot sight. Follow the path from the beach to the facility, use the Cartographer terminal, and climb back to the surface. Press **E** near the Pelican's rear ramp once it reaches the landing zone. The adapted entry leaves the security door open so the route starts at the descent.
To launch that section directly, run `./scripts/play-macos.sh '-ehalo_section 4 2'`.

### Retail collision for other sections

The engine plays any section on the original structure collision when `packages/maps/<section>.hcol` exists and loads (`Halo: loaded N retail collision surfaces for <section> (M static machines)` in the log); a missing file means stock AssaultCube geometry, and a file that fails validation is reported (`retail collision unavailable`) and also falls back to stock geometry. `tools/import_halo_campaign.py --collision validated|all|none` chooses the sections that get one: `validated` (the default) covers the missions in `VALIDATED_COLLISION` (a10, a30, a50, b30, b40, c10, c20, c40, d20 and d40) except the sections in `STOCK_SECTIONS`, which keep stock geometry (and need no `.hcol` in `package-macos.sh`); `all` writes every section, `none` removes them. For those sections the importer also

- projects each section's BSP with that section's own projection (b30's return reuses section 1's, which is why `halo_b30_03.hcol` is identical to `halo_b30_01.hcol`),

### Falls, wedges, lifts and light bridges

None of this has been verified in the game yet: it was written while testing was on hold. `tests/test_retail_recovery.py`, `tests/test_traversal_routes.py` and the lift and bridge walks of `tests/test_retail_collision.py` (`PENDING_WALK`) check it once testing resumes.

- Falls out of the world. On retail collision a body can fall through a hole or seam in the structure, which the stock cube grid never had. The engine (`updateRecovery` in `source/src/halo.cpp`) keeps the last eight retail floor spots the player stood on, at least 2 units apart (only real structure floor counts: not a lift deck or a light bridge, which move or vanish). A player whose feet are more than 8 units below the section's mesh, or who has been in the air for two seconds with neither structure nor device below down to that depth, is put back on the newest of those spots that is still clear (`Halo recovery: fell below the retail collision, player put back at x,y,z`, or `fell out of the world`). A second recovery within five seconds goes one spot further back. If none is clear, the player dies and reverts to the checkpoint as usual. Actors (enemies and allies) whose feet fall below that depth die, as in Halo. Ordinary falls, into a pit with a floor, or d20's jump into the shaft its exit volume hangs in, never reach that depth or that airtime over nothing, and the checks do nothing on stock geometry, during cinematics or once a section is complete.
- Wedges. A player whose body overlaps the structure by more than 0.1 units or is inside a device's box (a door or a lift deck closing on them) for 0.75 s, or who has been in the air without moving at all for 1.5 s (caught in a crease too steep to stand on), is moved to the nearest clear retail floor within 3 units (`wedged in the collision`, `stuck in mid-air`), or failing that to a safe spot as above. A player wedged before standing on any retail floor since the last move that was not walking (a spawn, a revert to a checkpoint on a lift deck, a teleport) is not reverted, which would put them back in the same place and loop: they are left where they are (`no safe floor since the checkpoint, player left in place`) and checked again five seconds later. A spot inside a vehicle's footprint (one parked there since) is neither recorded nor used. None of these checks run while the player is in a vehicle seat; the vehicle has its own stuck recovery (see Vehicles). A player thrown out of a vehicle onto it, with no room for the body beside it, whom these checks find wedged or falling within 15 s, without having taken a seat since, is put back in that seat instead (not after the vehicle itself fell out of the world), the vehicle righted where it lies or moved to where it fits (`Halo recovery`'s reason, then `player put back in the Warthog at x,y,z`): in the Maw's run the driver has never stood on retail floor, and this used to log `player left in place` every five seconds. Moves that are not walking reset this recovery (see the next item).
- Moves that are not walking. Every move of the player other than walking goes through one helper, `haloplayermoved` in `source/src/halo.cpp`: a spawn or revert, Continue, a section start (BSP switches end a section, so this covers them), the end of a cutscene (the Cartographer's handoff moves the player; every scene's end is treated the same), getting into a vehicle seat (the scripts' `vehicle_load_magic` and `unit_enter_vehicle`, a revert or the Maw's escape seating the player, a reclaim) and out of one (beside it, or thrown onto it), and every QA hook that teleports the player (`tests/native/*.inc`, except `qa_retail_recover`, which stands in for a fall or a wedge). It drops the safe spots recorded before the move, so the recovery never puts the player back on a floor from before a teleport, restarts the wedge and stall timers, and starts a one-second grace in which the wedge and stall checks do not count (the falls are still checked): a wedge right after a move is nudged after 1.75 s instead of 0.75 s. Getting into a seat keeps one safe spot, the retail floor the player got in from: when the vehicle falls out of the world with no safe spot of its own, the driver goes there (`halorecoverplayer`) rather than dying. With `halo_scripttrace 1` each move is logged (`Halo moved: <why>, N safe floors dropped`). The mission scripts' player teleports (`object_teleport` of the player, as in d20's captain scene and d40's bridge) are still not performed, so they do not move the player. Not verified in the game: `tests/test_retail_recovery.py` checks it (`qa_halo_moved`).
- Lifts. Everyone standing on a lift's deck is carried with it: the player, allies and enemies, on retail collision as on stock geometry. On a rising deck a body counts once any part of it is over the deck, as the device collision stands it there, so the deck no longer lifts into someone on its edge and wedges them (only the player whose centre was over the deck used to be carried). A descending deck carries only the bodies whose centre is over it, so someone standing on the landing beside a flush deck is not dragged down through the landing's floor. A lift's deck at rest may stand higher above its landing than a step: the Library's platforms are 0.38 units up at the bottom of their shafts, 2.6 units at floor 1's scale, against a 1.26-unit step. A grounded body may step onto a lift deck from up to 0.45 retail units below its top (`Scenario::liftBoard`); nothing else changes the step height. The device's collision is its boxes in the current animation pose, so it moves with the lift.
- Light bridges. A light bridge is a machine whose panels slide out over a pit; the engine collides with each panel's box in its current pose, so an extended bridge is floor and a retracted one leaves the pit open. A bridge that retracts under the player (c10's flickering `bridge_c`) drops them into the pit; if the pit has no floor, the fall recovery puts them back on the last floor they stood on. The route planner models them as above (`LightBridges`).
- The QA walker (`tests/native/retail_qa.inc`) boards, calls and sends lifts at deck rows, waits two rows short of a light bridge until it is extended, and after a recovery carries on from the nearest route row behind it. See `tests/README.md`.

## Presentation

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold; nothing of it has been seen or heard. `tests/test_presentation.py` is written but has not been run. The code is `source/src/halo_fx.cpp` (`halo_fx.h`); apart from the melee lunge (below), none of it changes the game's state (no damage, no movement, no script results).

```bash
python3 tools/halo_weapons.py "$maps"                    # zoom-in, zoom-out and loop sound roles
python3 tools/halo_vehicles.py "$maps"                   # engine, crash and suspension sounds
python3 tools/halo_effects.py "$maps"                    # packages/halo/effects.txt
python3 tools/import_halo_audio.py "$maps/a30.map" .     # decodes them; tags/classes.txt
```

`import-macos-assets.sh` runs `tools/halo_effects.py` before the audio import and `package-macos.sh` requires `effects.txt`. All of it is generated and git-ignored. The new `sound` roles and lines are skipped by older games and the tables keep their formats (weapons.txt 3, vehicles.txt 2).

- **Script effects.** `tools/halo_effects.py` reads every `effe` tag a mission script names (the effect constants of `effect_new` and `effect_new_on_object_marker`, and d40's effect globals such as `explosion_large`; 20 tags) and writes, per effect, a kind (explosion, burst, smoke or glow), a size (1.6 for the tags' large particle systems, 0.6 for small ones and grenades), its first light (radius, colour, duration), the area radius of its strongest `jpt!` part and its first sound. `effect_new <effect> <flag>` draws it at the cutscene flag's place in the section, `effect_new_on_object_marker <effect> <object> <marker>` at the object's marker (batch 9: the marker of the object's model from the `.hscb`, in the model's bind pose and the object's frame, as the seats are placed, so an animation does not move it; the object's origin when the model has no such marker, and for the player and actors). Every retail call is in a cinematic (the cyborg chip insertion at chief's and cortana's hands), where an effect only plays its sound, so the markers only place effects outside scenes. AssaultCube's particles stand in for the tags' particle systems: an explosion is a fireball (three for the large ones), sparks, smoke and a flash, and knocks the camera within three times its radius; a burst is sparks and a flash; smoke is smoke; a glow a flash and a few plasma sparks. The effect's light lights stock geometry only (the retail mesh keeps its lightmaps). The tags' particle systems, decals, debris and damage are not converted: Halo's `pctl` and `part` tags carry their own shaders, bitmaps and physics, which AssaultCube's fixed particle types cannot show without a particle renderer of their own, and the damage is left out on purpose (d40's escape sets explosions off along the route, and with the flags projected onto AssaultCube's maps a damaging one could kill the player where Halo's would not). In a scene, whose flags and objects are in the scene's frame, an effect only plays its sound, unpositioned. An effect the table does not have still draws (an explosion when its name says so, else a burst; logged with `halo_fxtrace 1`).
- **Camera shake.** `player_effect_set_max_translation` (world units), `player_effect_set_max_rotation` (degrees: yaw, pitch, roll), `player_effect_set_max_rumble` (the controller's motors, 0 to 1: a fine fast tremble here), `player_effect_start <intensity> <attack s>` and `player_effect_stop <decay s>` shake the view; `player_effect_impact` and `player_effect_rumble` are a half-second knock. Vehicle crashes (the player's vehicle), the explosions above and grenade, rocket and other blasts within three times their radius knock the camera too. The shake moves only the rendered view (`transplayer` and the sky), never the player's yaw, pitch or position, and is smooth noise of the time (it does not draw on the game's random numbers); the player's shots still go where the shaken view's centre (the reticle) points, since the aim point is read from the drawn frame. It is capped at 8 degrees; `halo_shake 0` turns it off. A checkpoint revert stops the shake and clears the cinematic screen effects and the damage arcs (the reverted script starts its own again); the sound class gains are kept.
- **GL resources (batch 9).** The blur's copy of the frame and the flashlight's spot texture are deleted when the GL context is rebuilt (`resetgl`, which a display or resolution change in the options runs: `cleanupgl` calls `halofxcleanupgl`) and made again on their next use; a texture name that stops being one some other way is caught by `glIsTexture` before each use. The copy is reallocated whenever the viewport changes size (a window resize without a rebuild). Without non-power-of-two textures (OpenGL below 2.0 and no `GL_ARB_texture_non_power_of_two`) the copy is the next powers of two and only its lower left is drawn; a viewport larger than the driver's texture limit gets no blur. `qa_fx_state` prints the copy's size, the texture's, `npot`, whether both textures are live and how often they were remade.
- **Cinematic screen effects.** `cinematic_screen_effect_start` turns them on and `_stop` clears them. `_set_convolution <iterations> <mode> <from> <to> <s>` blurs the view from one radius to the other (retail radius in 480-line pixels): the frame is copied once and laid back over itself in up to three rings of eight offset copies. `_set_filter <desaturation from> <to> <tint from> <to> <additive> <s>` with `_set_filter_desaturation_tint <r> <g> <b>` takes the colour out of the view towards the tint, approximated without shaders (a multiply towards the tint and a grey wash); `_set_video <mode> <intensity>` (c10) draws scan lines and a cold cast. They draw over the 3D view and under the HUD and the scenes' letterbox and fades; `halo_screeneffects 0` turns them off.
- **Flashlight.** **X** (`halo_flashlight`) turns it on and off. Its light is the cyborg's `characters\cyborg\flashlight_cyborg`: 6 world units of radius, full inside 20 degrees and none past 45. On the retail mesh it is a pass after the solid surfaces that adds each surface's own texture lit by a spot projected from the eye, fading to nothing at the radius; on stock geometry it is an AssaultCube dynamic light a little ahead of the eye. Actors and models are not lit by it. It drains over 60 seconds on and recovers over 30 off (an engine choice: the tags hold no flashlight energy), and the retail HUD's flashlight meter shows its charge while it is on. It goes off at a section start and when the player dies.
- **Damage-direction indicator.** A hit on the player from an actor, the shield's included (a hit the shield takes whole used to show nothing), draws a red arc round the reticle towards where the attacker was, in the world (it follows as the player turns), fading over a second; hits from about the same way renew one arc, up to eight. It replaces AssaultCube's own indicator in the campaign; `halo_damageindicator 0` turns it off.
- **Sound classes.** `sound_class_set_gain <class> <gain> <ticks>` fades every retail sound class whose name starts with the given one (`vehicle` is `vehicle_collision` and `vehicle_engine`, `ambient` the three ambient classes) to the gain. It reaches the scenario's sounds (music, ambience, dialogue: `tools/halo_effects.py` writes each cache's `snd!` classes, and the channels already playing follow the fade), the decoded tag samples the engine plays (weapon, grenade, equipment, vehicle and effect sounds: `tags/classes.txt` from the audio import) and the engine loops. AssaultCube's own samples (footsteps, the fallback weapon sounds) have no class and are not faded. The gains go back to 1 at each section start and on Continue (they are not in the progress file: a class the script had faded before the save plays at full gain until the script sets it again).
- **Vehicle sounds.** `tools/halo_vehicles.py` adds the tag's sounds to `vehicles.txt`: the engine loop (the first looping sound attached to the vehicle: `warthog_7_engine`, `ghost_lp`, `banshee_engine`, the Scorpion's `warthog_engine`, `wraith_eng1`, the turret's `c_turret2`), the crash (`jeep_hit_solid`) and the suspension (`warthog_suspension`, the Scorpion's own). The engine loops from whoever drives (a turret's while its gunner turns it faster than 15 degrees a second, held for a quarter second), its pitch rising with the speed, and stops when nobody does; the crash plays when a vehicle loses more than a third of its top speed in one step against a wall, a body or another vehicle, the suspension on a landing faster than 14 units per second down, at most one of them every 0.4 s.
- **Weapons.** Zoom steps play the weapon tag's zoom-in and zoom-out sounds (`weap` +408 and +424 after the item section: the pistol's, sniper rifle's and rocket launcher's `sniper_2x_zoom` and `sniper_10x_zoom`). A looping sound attached at a trigger marker is the weapon's `sound loop`: the flamethrower's `fire_ft` (its only firing sound) plays while the trigger is held and it can fire, and the plasma pistol's `charge` hum once a charge has built for 0.15 s.
- **Melee lunge.** A hostile actor in sight within 1.8 times the blow's reach (7.2 units) and 25 degrees of the aim takes the blow, and the player is pushed towards it by a velocity impulse that the floor's friction takes out (about 1.9 units travelled per unit of impulse, closing the gap to about 3 units), as an explosion's knockback is applied; the movement constants are untouched. `halo_meleelunge 0` turns it off; `halo_meleetrace 1` logs it.
- **Rocket launcher.** Its tube rides the right shoulder with its top above eye height; in AssaultCube's wider view (75 degrees vertical for the weapon, where Halo's view is 70 degrees horizontal) it filled the right of the screen. It is now drawn 0.5 units further right, 1 forward and 1.5 lower than its retail animation holds it. This is a judgement call made without seeing it: `halo_viewmodeloffset <right> <forward> <up>` changes the current weapon's placement in the game (no arguments prints it), for tuning, and the values belong in the table in `source/src/halo.cpp`.
- **Reticles.** Vehicle guns use their own retail reticles where the HUD tags carry them (the turrets, Warthog, Ghost, Scorpion, Banshee and Wraith guns all do). A weapon whose HUD tags have no reticle (the flamethrower, whose weapon HUD is empty) gets a plain one, a circle and four ticks in the retail blue (red on an aim-assist target), and shows its rounds or battery as text; without `hud.txt` a seat's gun gets the plain reticle too.

## Vehicles

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold, the vehicle fixes (bodies inside vehicles, shoving, stuck recovery, the escape taking over a scenario Warthog, lift decks, routes round parked vehicles) included. `tests/test_vehicles.py` (items 7 to 9 for the fixes), `tests/test_maw_drive.py` (item 6) and the parked-vehicle check in `tests/test_traversal_routes.py` are written but have not been run.

`tools/halo_vehicles.py "$maps"` (run by `import-macos-assets.sh` before the campaign import) writes `packages/halo/vehicles.txt` from the retail `vehi` tags and exports their models to `packages/models/halo/vehicle/<name>` (git-ignored, like everything under `packages/`). It lists six vehicles in a fixed order: the Warthog (a car), the Covenant gun turret (a fixed gun with a gunner seat), the Ghost (a hover craft), the Scorpion (a tank), the Banshee (a flyer) and the Wraith (a hover craft the player may not drive); see Enemy and flying vehicles. Each record carries the class, whether the player may drive it (format 2; the game still reads format 1 tables, giving their props a class from the retail motion kind), the drive parameters, the model's bounds, the seats with their markers and the vehicle weapon from `weapons.txt`. `package-macos.sh` requires the file. Without it the engine falls back to a built-in Warthog with the model the actor importer writes to `packages/models/halo/warthog`; a vehicle with no model is drawn as a wire box.

`tools/import_halo_campaign.py` writes each mission's scenario vehicle placements (the `scnr` vehicle block) of those six types into the sections whose BSP holds them, as `PLAYERSTART` entities with team 102: the type, the placement's not-placed flags, the scenario object index and the section scale. On retail collision they stand at their retail point and settle onto the floor; on stock geometry they go on the nearest raster floor. Placements the scripts create (`object_create`, not-placed flag 1) appear when the script creates them; the others appear at the start, except on the difficulties their flags leave them out of. Re-run the campaign import (all missions) to place them. Imported: d40's six parked escape Warthogs in section 6, a Warthog and a turret in section 7 and the two enc7_7 turrets in section 8; a50's 14 turrets; the Warthogs, Ghosts and Banshees of a30, b30 and c40; b40's turrets, Ghosts, Wraiths and Banshees (its Scorpion stands outside every campaign section); the turrets of c10 and d20. Pelicans, dropships, lifepods and cinematic props are left out.

`source/src/halo_vehicle.cpp` runs them:
- **E** by a seat's door gets in (the driver's door of a Warthog, its rear for the gunner's seat, a turret's gun); in a seat **E** gets out beside the door, or on the other side, behind, ahead or on top, wherever the body fits, and stays in when none does. A seat nearer than a weapon on the ground wins **E**. The HUD prompts `E  Drive the Warthog`, `E  Warthog gunner`, `E  Man the Covenant Turret` or `E  Flip the Warthog`.
- The Warthog drives with **W**/**S** (throttle, brake, reverse) and steers towards where the camera looks, as the retail Warthog does; **A**/**D** steer directly. `halo_vehiclesteer 1` steers with the keys only. The camera orbits behind with the mouse. Top speed is the retail Warthog's at the section's scale, and never below 36 units/s (the old escape pace, which the 3:00 timer was set for); grip is strong with some slide, it climbs and jumps off crests, pitches and rolls with the ground, and flips when it lands on its side or back or stands over more than 58 degrees. Upside down for 0.7 s it throws the driver out; **E** beside a flipped vehicle puts it back on its wheels. Running into actors at speed kills them. It is not the retail physics.
- The bodies are the retail vehicles' size at the section's scale. On retail collision the Warthog drives on four wheel traces and two chassis capsules against the structure and the machines (doors); on stock geometry on the cube grid (it steps up whole cubes as the walking body does). Bodies collide with vehicles (`halo_vehiclecollide 0` turns that off, for checking a route walk a placed vehicle blocks); the walking routes go round the parked ones (above).
- Bodies inside vehicles. A body (the player on foot or an actor not in a seat) left part way inside a vehicle's box, by a vehicle the script creates, spawns, teleports or a revert puts back over it, an exit spot or a lift, is pushed out within a frame by the shortest way that has room, checked against the retail collision (or the cube grid), the devices, the other bodies and the vehicles: out of each face at the box's edge, its corners, each face a body's width further out, nearest first, or onto the roof when the feet are within a step of it; first onto floor, then over a ledge, never through a wall or a closed door between the body and the spot (a line of sight at the body's middle) (`Halo vehicle: player pushed out of the Warthog (N units)`, actors with `halo_vehicletrace 1`). A body with no room anywhere may walk out of that vehicle and is tried again every quarter second (`... has no room to get out; it may walk out`). The old rule, by which only a body deep inside a box could walk out and one part way in could not move, is gone. Ordinary movement is unchanged: walking never enters a vehicle's box.
- A moving vehicle (the player's Warthog, or an empty one rolling) shoves each body it runs into out ahead of it or aside, a few hundredths of a unit clear, every 8 ms step; a body pinned against a wall (or another body or vehicle) stops it instead. The player's Warthog at more than 8 units/s still runs actors down as before, once a frame each (killed outright above 20).
- The Warthog's gunner seat and the turrets fire their retail gun (warthog gun, turret gun) at the crosshair with its rate and heat; the driver cannot fire. The HUD shows the vehicle, the seat, the speed or the gun's heat, and the shield, health and motion sensor. Fire on a player at the wheel of a Warthog is cut by a fifth; the Warthog, the Scorpion and the turrets cannot be destroyed (their collision models have no body vitality, as in Halo CE), the Wraith, and the Ghost and Banshee while ridden, can (Vehicle damage, batch 7).
- Stuck recovery (`updateStuck`), as for the player on foot. Each Warthog keeps its last four safe spots, sampled every quarter second: grounded, upright within 30 degrees, clear of the structure, the machines and the other vehicles, with all four wheels on structure floor (not a lift deck or a light bridge), at least half a length apart. **Classes.** `source/src/halo_vehicle.cpp` drives four classes. The Warthog is the car described under Vehicles. The Ghost and the Wraith are hover craft: they float a little (0.12 world units) over the ground the wheel traces find (the model is drawn that far up, bobbing; the body's box covers it), turn on the spot towards the camera at their own rate (the tags' turn rate is 0, so the Ghost turns 150 degrees a second and the Wraith about 60, slower with their lower retail speed), strafe with A and D and slide, and never flip. The Scorpion is a tank: A and D turn it on its tracks, W with no key held steers towards the camera, and it barely slides. The Banshee is a flyer: piloted, it has no gravity, its heading and nose follow the camera (100 and 70 degrees a second, the nose within 55 degrees), it banks into turns, W pushes along the nose (S slows and backs it), A and D strafe, jump climbs and crouch descends (`halovehiclejump`, `halovehiclecrouch` from `physics.cpp`), and with no input it hovers in place; it slides along the structure, machines and vehicles it meets and may rest on the floor. The actor in an armed seat (a Ghost's, Wraith's, Scorpion's or Banshee's driver, a Warthog's or turret's gunner) fires the vehicle's gun at its brain's target instead of its own weapon (`halovehiclearmedseat`): within the gun's range, within the nose's cone for a fixed gun, in bursts of 0.9 to 1.8 s for an automatic gun, leading the target by most of the shot's flight, with the variant's aiming error; the Wraith lobs its mortar at the angle that lands it at the target's distance (the engine's projectiles keep their speed and bend under gravity, so the angle is the distance times gravity over twice the speed squared; at 10 world units a second the mortar reaches about 85 units), and a Banshee pilot adds a fuel rod every 5 to 9 s inside 35 units. ### Vehicle damage and the vehicle actor variants (batch 7)

**Not verified in the game yet**: written and compiled while testing was on hold; `tests/test_vehicle_damage.py` checks it and has not been run. Re-run `python3 tools/halo_vehicles.py "$maps"` and `python3 tools/halo_effects.py "$maps"` (both git-ignored outputs); the death explosion's sound (the frag grenade's) is already decoded by `tools/import_halo_audio.py`.

- **The table.** Each `vehicles.txt` record gains `vitality <body> <coll flags> <material type> <body multiplier>` from the vehicle's collision model (`coll`: maximum body vitality, its flags, the material type and body multiplier of its indirect damage material), `destroyed <effe>` (the body depleted effect), `variant <actv>` (the actor variant named after the vehicle, `<vehicle tag> pilot` or `gunner`: the retail vehicle variants reference no unit, so the match is by name) and each seat's unit seat flags as a ninth column. Older engines skip the new lines and column; the format stays 2. The retail values: the Wraith 450 with no flags; the Ghost 160 and the Banshee 100, both "only damaged while occupied" (flag 64), the Banshee also "takes body damage for its children" (2); the Warthog, the Scorpion and the turret 0 (indestructible, "only damaged by explosives"). All three destructible ones use the Wraith's death explosion; their material is metal_thick (7). The Wraith's driver seat is invisible (seat flag 1). `effects.txt` (`tools/halo_effects.py`) now also holds the vehicles' depleted effects, so `halofxeffect` draws and sounds the death explosion.
- **What hits a vehicle.** A vehicle with a body vitality stops shots: an instant shot (`halofiretrigger`) and a bolt in flight (`haloupdatebolts`) end on the first such vehicle's body box (yaw only) they pass through (`halovehicletrace`), unless the body they met is a rider of that vehicle in an open seat (the Ghost's pilot is still shot off it); a rider in an invisible seat (the Wraith's driver) or of a vehicle that takes its children's damage (the Banshee's pilot, the player included) is covered, and the vehicle takes the shot. A blast (rockets, fuel rods, mortars, the Scorpion's shell: `areadamage`; frag and plasma grenades) damages every such vehicle whose box is within its outer radius, at the falloff to the box's nearest point (a grenade also needs a clear line to the box's middle; the one a plasma grenade is stuck to takes full strength plus the attached damage). A shot never stops on the shooter's own vehicle (a blast does reach it, as it reaches the shooter's body: a fuel rod fired point-blank hurts the Banshee that fired it). An actor's shots stop only on a vehicle someone hostile to it rides, as they pass through friendly bodies (`haloactorhit`): a Covenant actor's fire passes through its own side's Wraith, or an empty one, as before (review judgement call: otherwise b40's Grunts firing at the player past their Wraith would wreck it); the player's shots stop on every such vehicle. The Warthog, the Scorpion and the turrets have no vitality: shots pass through them as before (a judgement call: no other behaviour changes for them). An empty Ghost or Banshee stops shots but takes no damage.
- **How much.** `halovehiclehit`: the hit's damage (range or blast falloff applied, the shooter's modifier included) times the jpt! modifier for the vehicle's material (`weapons.txt` and `equipment.txt` `materials` lines: small arms 0.25 on metal_thick, explosives 1) and the material's body multiplier, over the body vitality. Enemy fire on the player's own vehicle is scaled by the difficulty as fire on the player is (`halodifficultydamage`); damage to any other vehicle is divided by the difficulty's enemy health (`halodifficultyhealth`). A vehicle "only damaged by explosives" takes only blasts; one "only damaged while occupied" only while someone alive rides it. Scripted cinematics hurt nothing. `halo_vehicletrace 1` logs each hit (`Halo vehicle N (Wraith) takes X from the player: health H`).
- **Destroyed.** At no health the vehicle explodes (its depleted effect at the box's middle, `Halo vehicle: the Wraith is destroyed`), its riders are put out and killed (a large finite hit, so `object_cannot_take_damage` and the QA walker's protection still hold, credited to whoever destroyed it), it no longer exists, and the scripts' object is destroyed as `object_destroy` does (`haloscenarioobjectdestroyed`: cargo set down, volume tests and object lists without it). `unit_get_health` of a vehicle's object is now its body health (1 for one with no vitality) while it exists and -1 once it is gone (b40's `dialog_ext_a_c` waits for `crev_ent_wraith_a` and `_b` to reach 0 or less; it used to wait for ever). A script's `object_create` brings it back whole; until then `vehicle_load_magic` and `unit_enter_vehicle` into it fail (one merely not created yet is still created by them, as before). The wreck is not left and the explosion deals no damage of its own (judgement calls).
- **Saved.** A checkpoint keeps each vehicle's health and whether it was destroyed; the progress file's vehicle records (version 3) carry them after the safe spots (a record without them, from before, still loads whole), and a destroyed vehicle restores as gone.
- **The vehicle actor variants (gap 13).** An actor at a vehicle's gun (a Ghost's, Wraith's, Scorpion's or Banshee's driver, a turret's or Warthog's gunner) now fires as the vehicle's actor variant (`variantOf`: the `variant` line, else the variant named `<vehicle tag> pilot` or `gunner` in actors.txt): its shots carry that variant's damage modifier (`halofiretrigger`'s `modifier`, which `rollshot` takes instead of the seated actor's own; the turret gunner's 0.333, the Ghost's, Banshee's, Scorpion's and Wraith's 0.5) and miss by its firing error (`aiFire`). A variant with no modifier (the Warthog gunner's, whose fire block is all zeros) is not used at all (`fightingVariant`): the seated actor's own modifier and error apply, so a marine at the Warthog's gun still misses by its own error rather than never missing. Before, an Elite's or Grunt's infantry modifier and error applied.
- QA hooks (`tests/native/vehicle_qa.inc`): `qa_vehicle_damage VEHICLE AMOUNT EXPLOSIVE` (as the player, no material modifier), `qa_vehicle_aim VEHICLE` (face its body box) and `qa_vehicle_protect 0|1` (`halo_vehicledamage`); `qa_vehicle_state` adds a `VEHICLE_HEALTH` line per vehicle (`name`, `health`, `destroyed`, `vitality`, `flags`, `material`, `occupied`, `variant` and its `modifier` and `error`).

## Retail weapons

`tools/halo_weapons.py` reads every `weap` tag in the ten campaign caches, follows each trigger to its projectile and damage tags, and writes `packages/halo/weapons.txt`. The game loads that table at startup. Rounds, reload time, rate of fire and its ramp, spread, heat, battery, charge time, zoom levels, aim assist, projectile speed and homing, and damage all come from the tags. The importer also records the first-person and pickup models from the asset library, so run it after `import_halo_library.py` and before `import_halo_campaign.py`. The campaign importer stores each enemy's carried weapon (from its actor variant) and the scenario's weapon placements in the section maps.

```bash
python3 tools/halo_weapons.py "$maps"
python3 tools/import_halo_campaign.py "$maps"
```

The player carries two of the nine campaign weapons. Walking over a weapon you carry takes its rounds, and **E** swaps the current weapon for one on the ground. **Mouse 2** or **Z** steps through the weapon's zoom levels. Holding fire charges the plasma pistol. Covenant weapons show battery and heat instead of rounds, and overheat. Enemies fire their actor's weapon with the variant's share of its damage (rolled and exact per shot, Damage fidelity) and drop it when killed. Zoom steps play the weapon tag's zoom-in and zoom-out sounds; a weapon whose HUD tags carry no reticle (the flamethrower) gets a plain one, and the rocket launcher sits a little lower, further right and forward than its animation holds it (Presentation; none of it seen in the game yet).

**Starting profiles (batch 8, not verified in the game).** A mission's player now starts with the scenario's player starting profile 0, not the old fixed assault rifle, pistol and two frags. `tools/import_halo_scripts.py` (`profile_rows`) writes every starting profile into the `.hscb` (version 9): the name, the starting health and shield modifiers, the primary and secondary weapons as retail tag paths with their rounds loaded and total, and the frag and plasma counts (scenario +840, 104-byte rows). The engine resolves the weapons against `weapons.txt` when it applies a profile (`haloweaponfind`), so regenerating the weapon table keeps them right. Profile 0 per mission: a10 none (the player starts unarmed, no grenades), a30 the assault rifle 60 + 120 and the pistol 12 + 64 with no grenades, a50 the sniper rifle 4 + 64 and the assault rifle 60 + 360 with four frags, b30 the rifle 60 + 240 and pistol 12 + 72, b40 60 + 300 and 12 + 96, c10 60 + 180 and 12 + 96 with four frags and four plasma grenades, c20 60 + 180 and 12 + 60, c40 the plasma pistol and the shotgun 12 + 48 with four frags and two plasma, d20 the rifle 60 + 240 and the plasma pistol, d40 the rifle 60 + 120 and the plasma rifle with two of each grenade (most with four frags; see `tests/test_starting_profiles.py`). A fresh start (a new mission, a section started on its own, Restart section without a carried loadout) takes profile 0 once the mission script is loaded (`applyStartingProfile` in `source/src/halo.cpp`), and that becomes the loadout a revert before the section's first checkpoint returns to; a section entered from the one before keeps what the player carried, and Continue what was saved. `FreshProfile` adds to a fresh start of a later section what an earlier section's script gives and a script started afresh there does not give again: a10's `bridge0_profile` (the pistol) from section 3 on. `player_add_equipment <unit> <profile> <reset>` is bound for the player: `reset` true replaces the loadout (c20's `easy_start` on Easy: the shotgun and pistol, four frags), false adds to it (a10's `bridge0_profile` at Keyes's bridge: the pistol into the empty selected slot); a weapon already carried takes the rounds, a full pair takes none. Judgement calls, not checked against the retail executable: "rounds total" is the reserve beyond the magazine, clamped to the weapon's maximum; a battery weapon starts charged whatever its rounds say; a modifier of 0 leaves health or shield as they are (a10's bridge profiles have 0), otherwise it is a fraction of full. With an `.hscb` older than version 9 (or without `weapons.txt`) the old default loadout stays. Re-run `python3 tools/import_halo_scripts.py "$maps"` after pulling this (version 9 files are the version 8 ones byte for byte up to the new trailer, but their hash changes, so a game saved before continues at its checkpoint with the script restarted).

**Empty weapon slots.** With `weapons.txt` a carried slot may be empty. An empty slot is AssaultCube's knife slot: nothing is drawn in the player's hands, no reticle (retail or fallback) shows, the fire button does nothing (`haloplayerunarmed`, `shoot` in `weapon.cpp`), melee still strikes (50 points, the fallback melee damage) and the retail HUD shows the unit panels without a weapon panel. A weapon picked up fills the empty slot and is selected (with both slots armed **E** swaps as before); switching weapons does nothing with one weapon or none. The progress file writes `empty <slot>` for an empty slot; a slot with neither a `weapon` nor an `empty` line (older saves, saves made without `weapons.txt`) gets the default weapon, as before.

**Damage (`jpt!`).** Weapons, melee and grenades read their damage with one layout, `JPT_*` in `tools/halo_weapons.py`, checked against the bytes of every campaign `jpt!` tag (not yet tried in the game). From the tag body: radius bounds at 0, cutoff scale at 8, flags at 12; the damage section at 452 holds side effect and category (two 16-bit enums), damage flags, the area core radius, then the damage lower bound at +12, the upper bound's min and max at +16 and +20, the vehicle passthrough penalty at +24, active camouflage damage, stun, maximum stun and stun time, and instantaneous acceleration at +48. The frag explosion reads 80 lower, 120-120 upper; the sniper bullet 101-101 with a 0.5 passthrough. `weapons.txt` is format 3 and `equipment.txt` format 2: `projectile`, `melee`, `blast` and `attached` lines carry lower, upper min and upper max, and format 3 adds to each `projectile` line the area's inner radius, the projectile's air damage range (`proj` +84 after the object section, two floats in world units) and the `jpt!` side effect. The game refuses older tables, so re-run `tools/halo_weapons.py` after pulling this. How the bounds are used is described under Damage fidelity below.

### Damage fidelity

Written while testing was on hold; nothing here has been run in the game (`tests/test_damage_model.py` checks it, and `tests/test_melee_materials.py` the batch 9 additions: the melee from behind, the AOE core, the needle supercombine; neither has been run).

**The jpt! bounds.** A full-strength hit deals a random amount in the upper bound's range; a weakened hit at scale s deals `lower + (full - lower) * s`, the reading of Halo's damage formula used here (the community tag definitions describe the lower bound as what a scaled hit falls to; not checked against the retail executable). Scale comes from:

- **Range falloff.** An impact closer than the near end of its projectile's air damage range deals full strength, falling linearly to the lower bound at the far end and staying there (a far end of 0 means no falloff). From the tags: shotgun pellet 1.5-3 world units (18-25 down to 8), plasma rifle bolt 20-50 (12-14 down to 10), plasma pistol bolt 20-50 (16-20 down to 10), Ghost and Banshee bolts 20-50 (10-14 down to 10), covenant turret bolt 0-100 (12-14 down to 8), Warthog chaingun 0-100 (16-24 down to 16). The assault rifle (5-15), pistol, sniper rifle, needle, the charged plasma bolt (5-20) and flame are flat (lower equal to upper), so their range does not matter. The distance is the shot's travel (hitscan: muzzle to impact) in Halo world units. Falloff applies to impact damage only, not to the blast of an exploding projectile (rockets, fuel rods, mortars, the Scorpion shell), and to the player's and the actors' shots alike.
- **Blast edges.** Area damage is full inside the inner radius and falls to the lower bound at the outer radius; beyond the outer radius there is none, so the blast steps from the lower bound to nothing at its edge. Grenades: frag 1.5-2.5, plasma 0.5-2.0 world units, both 120 at the centre and 80 at the edge. Exploding projectiles now use their inner radius too (rocket 0.5-2.0, 300-330 down to 80; fuel rod 0.5-1.5, 75 down to 40); before, they fell to none at the outer radius. The `jpt!` cutoff scale is zero in every campaign tag. The AOE core radius (batch 9; frag and plasma grenades 0.4, rocket 0.6 world units, a `core` line after the projectile or blast, older games skip it) is read as the radius within which the blast is at full strength and, for a grenade, reaches a body even when the line of sight from its centre is blocked (a grenade at rest against a wall or the floor has its centre a hair inside it). Only the rocket changes: full strength out to 0.6 instead of 0.5. This reading is an engine judgement, not checked against the retail executable; `halo_aoecore 0` ignores the radius.
- **Melee** keeps the full-strength roll (50-60; the flamethrower 70-80). The melee tags' radius bounds are 0.5-0.5, which gives no scale between full strength and the lower bound, so there is no sensible mapping for the lower bound (40). Every campaign weapon's melee carries side effect 2, "lethal to the unsuspecting" (Halo's kill from behind), which is now modelled (batch 9): the `melee` line has a fourth field, the side effect (the energy sword's is 3, EMP), and the player's melee on an actor from behind (the player more than 120 degrees off where it faces) that is not fighting the player (`ai_status` below combat, or its target someone else) deals the actor's whole shield and health, whatever the shield's modifier for the blow (`DAMAGE_UNSUSPECTING` with `halo_damagetrace 1`). A body its material leaves unhurt stays unhurt (the Monitor; a Hunter's shield arm can never be behind it), the player's empty-handed blow carries side effect 2 too, and the actors' melee is not affected. `halo_meleeunsuspecting 0` turns it off. The 120 degrees and the awareness rule are engine judgements.

**Grenades by thrower.** The player's grenades roll the retail full-strength range (120, and a stuck plasma grenade adds its attached 120). Grenades thrown by actors roll from the lower bound, 80 to 120, the balance they had before the `jpt!` layout correction, for the blast and a stuck plasma grenade's attached damage alike; with the edge falloff their blast deals 80 to 120 anywhere inside the outer radius. Against the player's 150 of shield and health on Normal an actor's frag at the player's feet deals 80 to 120 (Heroic 104 to 156, Legendary 136 to 204), and at the edge of its blast 80 (it dealt nothing there before).

**EMP.** Side effect 3, carried by the plasma grenade's blast and attached damage and by the plasma pistol's charged bolt (and the needle supercombine, below): the shield the hit reaches is drained to nothing after the hit is taken, the player's (its overshield layers too, ending the powerup) and any actor's (Elites; Jackals' shields count too). The hit itself is absorbed as usual, so EMP does not add damage to health. Vehicles inside a plasma grenade's outer radius, the one it is stuck to and one a charged bolt hits are stunned for 2 s (`HALO_EMP_STUN_MILLIS`; the tags' stun times are all zero, so the duration is the engine's): a vehicle's throttle does nothing (it coasts and steers; a hover craft does not strafe either, a Banshee sinks), whether the player or an actor is at the controls, and the seat's gun cannot fire, the player's or an actor gunner's. Charged bolts now stop on a vehicle's body; other shots still pass through vehicles. Stunning a vehicle is Halo 2's behaviour more than Halo CE's; it is here because it was asked for.

**Needle supercombine (batch 9).** The needle's projectile has the "has super combining explosion" flag (0x8) and a super detonation effect (`proj` +16: `weapons\needler\effects\explosion`, whose `jpt!` `weapons\needler\explosion` deals 60, falling to 40 over 0.5 to 1.0 world units, side effect 3, EMP), now written as a `supercombine <timer> <inner> <outer> <lower> <upper min> <upper max> <side effect> <category>` line after the needle's projectile (timer 0.75 s, the stuck needle's detonation timer) and a `sound supercombine` line (`needler_super_expl`, decoded by the audio import). The player's needles that strike one body (any body but the player's) count while they are stuck, each for its 0.75 s; when seven are stuck at once they detonate together at the body: the super detonation's area damage from the player (the shields it reaches drained, the vehicles in it stunned) and its sound (`SUPERCOMBINE` with `halo_damagetrace 1`). The tags hold no needle count: 7 is the engine's (about what the needler's full rate of fire, 10 a second, lands inside one timer), `halo_supercombine N` changes it and 0 turns it off. The needles themselves still deal their damage when they strike (not after their timer), and the actors' needles on the player do not combine.

**Enemy fire.** Every actor shot now rolls the weapon's full-strength range (upper min to upper max), applies the range falloff, and multiplies by the variant's damage modifier (0.5 without one); halodamage then applies the difficulty and the vehicle cut. The amount stays fractional: `halohit` hands it to halodamage, the shield takes its exact share, and the health damage keeps the fraction to the next hit (per target), so a 6.5 bolt costs 6.5 points on average where the slot damage dealt 6 or 7. An actor's shot deals at least 1 point, the floor the integer slot damage had. That floor is the one retune: without it the Sentinel beam (1 x 0.5) would take twice as long to kill. The player's shots go the same exact way (their rolls are unchanged). `halo_damagetrace 1` logs every hit halodamage sees (`DAMAGE_TRACE`).

## Grenades, equipment and weapon audio

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold. `tests/test_combat_equipment.py` is written but has not been run.

`tools/halo_weapons.py` also writes `packages/halo/equipment.txt` (git-ignored like the rest of `packages/`) and adds `sound` and `ammo` lines to `weapons.txt`. The equipment table holds the globals' two grenade types (carried maximum, the thrown projectile's fuse, whether its material responses attach it to units, the detonation's blast radius and damage and a stuck grenade's attached damage, the throw and explosion sounds), every campaign `eqip` tag (its powerup kind and time, pickup sound and pickup model, and the weapons whose magazines take it as ammunition) and the interface's low-shield and low-health sounds. `package-macos.sh` requires the table. - **Grenades.** **G** throws the selected type, **H** (`halo_grenade_switch`) switches to the other type when you carry some. ## Actor AI

`tools/halo_actors.py` writes `packages/halo/actors.txt` from the campaign `actr` and `actv` tags: vision and hearing, firing range, rate and error, burst timing, combat range, target leading, grenades, vitality, shield-based hiding, panic chances, berserk thresholds and position hold times; format 2 adds each variant's unit team, unit melee and collision materials (Factions and special enemies). Run it after `halo_weapons.py`. `import_halo_scripts.py` then writes version 6 `.hscb` files. These add each encounter's combat positions, squad states and position-group masks, platoon rules, per-start variants and command lists, and the scenario's command lists.

The campaign ending is driven by the scripts. `game_won` on The Maw's last section, or the finale cue finishing that section, starts an ending: a credits roll over the level (Enter skips), `config/halo-progress.txt` marks the campaign beaten (`beaten 1`, with every mission unlocked and no game left to continue), and the game opens the title menu (**Halo**) over the level (until this batch it opened the **Halo Campaign** pause menu; the change is not yet verified in the game). `game_won` on earlier sections is ignored, because sections advance on their own. `game_lost` kills the player so the normal revert applies.

Campaign bots think with `source/src/halo_ai.cpp` instead of AssaultCube's bot AI. AssaultCube still handles movement, pathfinding and physics. Actors:
- notice targets inside their vision cone, or hear gunfire, after a reaction delay
- alert nearby squadmates
- take combat positions from their squad's groups for attacking, defending or pursuing
- fire in retail bursts and throw grenades
- hide when their shields are low, panic when friends or leaders die, and go berserk when badly hurt
- follow command lists.

Marine and crew encounters now spawn on the player's side and fight the Covenant and Flood. Platoon rules switch squads between attacking and defending as casualties mount. The scripts' AI commands work, including `ai_actors` lists, `ai_status`, `ai_living_fraction`, `ai_strength`, magic sight, follow and fight orders, `ai_migrate` to new positions, command lists and their status, and `objects_can_see_*`. Vehicle seat and boarding commands act on the engine's vehicles and on dropships and Pelicans (see Vehicles, and Enemy and flying vehicles); for other vehicles they are stand-ins. The AI, unit and object-state commands live in `source/src/halo_script_ai.inc`. `ai_berserk`, `ai_grenades`, `ai_allow_dormant`, `ai_maneuver_enable`, `ai_renew`, `ai_prefer_target`, `ai_follow_target_ai`/`_disable`, `ai_follow_distance`, `ai_braindead_by_unit`, `ai_free`, `ai_try_to_fight_nothing`, `ai_link_activation` (waking the linked encounter once one is alert), `ai_teleport_to_starting_location*`, and the migrations (`ai_migrate_by_unit`, `ai_migrate_and_speak`, `ai_attach` on an actor) change what the actors do; flags survive a revert. `object_cannot_take_damage`, `unit_impervious` and `unit_doesnt_drop_items` apply to actors and the player, `unit_set_current/maximum_vitality` set the player's health and shield (maximum shield 0 removes the shield) or an actor's fraction of spawn health, `unit_suspended` stops an actor thinking, and `object_set_permutation door_off` removes a cell door and its collision. `damage_object` and `damage_new` do not read the retail `jpt!` effects: names with guaranteed, doom, plummet or death kill, any other effect does 40 damage. `ai_attach` on a scripted biped in play makes it an actor of the squad (Factions and special enemies, Attached actors and story figures). Recorded but without visible effect: `unit_open/close`, `vehicle_hover`, `object_set_collideable`, `unit_set_enterable_by_player`, `ai_attach` on other scripted objects and inside scenes, `ai_attach_free` on scripted objects, `ai_automatic_migration_target`, `ai_exit_vehicle` and `ai_vehicle_enterable_*` on vehicles the engine does not drive, `ai_allow_dormant` (no dormancy exists), `unit_set_emotion`, flashlight state and `ai_dialogue_triggers`. `(player0)` now evaluates to the player and `(player1)` to nothing. Balance has only been checked in short QA runs: enemies are accurate at close range.

Only living actors count towards the 128-actor cap on scripted placements; dead squad entries stay for `ai_living_fraction` and to stop a killed start respawning. The Flood life cycle is not scripted: a dying Carrier Form bursts into 4 to 8 Infection Forms, Infection Forms walk to a fallen marine or Elite (bodies last 90 s) and, on contact, are spent and turn the body into a Flood combat form 2.5 s later, and Infection Forms leap at a target 2.5 to 7 Halo units away every 1.5 to 3 s. These extra forms are not part of any encounter, so `ai_living_count` ignores them.

## Factions and special enemies

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold. `tests/test_factions.py` checks it and has not been run.

Re-run the tables and the models after pulling this (all git-ignored under `packages/`):

python3 tools/halo_actors.py "$maps"           # actors.txt format 2
python3 tools/import_halo_campaign_actors.py "$maps" .   # adds halo/monitor, halo/keyes, halo/engineer

The game still loads a format 1 `actors.txt` (variants then take their family's side and have no materials) and weapon tables without `materials` lines (every modifier 1; Hunter armour falls back to the values below).

**Teams and allegiances.** The engine has six teams (`halo_ai.h`): Covenant, human, Flood, Sentinel, player and "other" (the retail teams 6 to 9). An actor's team is its encounter's team, or on the default team its unit's default team from the biped tag (`actors.txt` `team`, read at unit +384: marines and crew human, Covenant and Engineers covenant, the Flood flood, Sentinels and the Monitor sentinel). Every team is hostile to every other except its own and the allegiances set; the player and the humans start allied (the missions also say so). `ai_allegiance` and `ai_allegiance_remove` set and clear an allegiance between two of the script's team literals, and the actors' targeting, hearing and shot hits follow the matrix at once, so Covenant, Flood and Sentinels now fight each other (c40, d20, d40) and c10 and c20's Sentinels fight beside the player. Allegiances reset when a mission starts, a checkpoint keeps them and a revert restores them, and saved games write them in the state block (`s allegiance <allied> <broken>`, optional on reading). Who counts as an ally (the motion tracker's yellow, enemies left in a wave, aim assist, `game_safe_to_save`, and the QA hooks that pick or clear hostiles: the route walker in `retail_qa.inc`, which also spares the passive Monitor and Engineers, `combat_qa.inc` and `damage_qa.inc`) asks the matrix. An actor whose target's team becomes an ally drops that target at once. A saved checkpoint writes the checkpoint's allegiances (not later betrayals); a mission or a section started afresh resets them even when it has no script. Infection Forms from a Carrier, and combat forms rising from bodies, are on the Flood team (they were Covenant).

**Betrayal.** When the player kills two members of a team allied with the player (the count is the engine's choice; Halo turns allies on a player who keeps killing them), the allegiance breaks: that team turns hostile, the console says `Halo: the human turn on the player`, and `ai_allegiance_broken` answers true for the pair (a50's `traitor_bitch`) until `ai_allegiance` renews it. Kills the scripts deal in the player's name (`ai_kill`, `ai_erase`, `ai_erase_all`, `damage_object`) do not count.

**Material damage.** `tools/halo_weapons.py` writes after every melee and projectile line of `weapons.txt` and after the grenades' blast and attached lines of `equipment.txt` a `materials` line: the `jpt!` tag's 33 damage modifiers, one per retail material type (`jpt!` +512). `tools/halo_actors.py` writes each variant's collision materials (`coll` +564, 72-byte entries: type, head flag, body and shield damage multipliers). For Hunters, Sentinels, the Monitor and Engineers `halodamage` multiplies the hit by the material's body multiplier times the weapon's modifier for that material; other bodies take damage as before, unless `halo_actormaterials 1` (batch 9, off by default: it changes every time to kill and is there for a later balance pass) applies the model to them too: the hit lands on the variant's head-flagged material at head height (the top fifth of the body, from the hit's point where the hit carries one: shots and the player's melee), else on its first other material, and takes that material's body multiplier times the weapon's modifier for its type (an Elite's flesh 1 for most weapons; the sniper rifle 0.05 and the assault rifle 0.65 on Flood combat forms; the plasma weapons 2 on Sentinels); an Elite's energy shield takes the weapon's modifier for the elite energy shield (30: the assault rifle's 0.7, which the engine applied to every shield before, the pistol's 0.8, the sniper rifle's and the plasma rifle's 2), and a shield a weapon cannot hurt (modifier 0) stops the hit whole; the body material's multiplier scales only what passes an Elite's shield (the shield takes the hit at its own modifier). Jackals keep their shields as before (their tags' modifiers are for the hand-held shield, which the engine does not place). Hits carry their `jpt!` (projectiles, blasts, grenades and the player's melee); a hit without one uses modifier 1 (0.5 on Hunter armour). `halo_damagetrace 1` logs `DAMAGE_MATERIAL` for these hits.

**Hunters.** From the tags: the shield arm (material hunter shield, body multiplier 0; every campaign weapon's modifier for it is 0 except the energy sword's) takes a direct hit from within 60 degrees of where the Hunter faces, so frontal fire does nothing; a hit from behind (beyond 130 degrees) lands on the exposed skin (hunter skin, multiplier 1, flagged as head: the pistol 1.0, assault rifle 0.5, shotgun 1.0); anything else, and every blast whatever the facing, lands on the armour plates (hunter armor: pistol and shotgun 0.2, assault rifle and plasma 0.5, frag and plasma grenades 0.25, rocket 1.0). The engine has no hit locations, so the region comes from the attacker's bearing and (batch 9) the height the hit struck: with `halo_hunterregions` (on by default) a hit in the top fifth of the body from outside the shield arm's 60 degrees lands on the skin (the coll's head-flagged material is hunter skin: the head bonus), and a frontal hit between 30% and 60% of its height while the Hunter fires its cannon (the 0.6 s after a shot, when the shield arm swings aside) lands on the skin of its belly. The heights, the firing window and the body as a cylinder are engine judgements, not the retail coll regions; blasts still land on the armour. Hunters pair off with the nearest unpartnered Hunter of their team (bond brothers) and rejoin a partner more than 10 units away; when one dies the other goes berserk for good and charges whoever killed it. Inside 1.6 world units a Hunter closes in and smashes: the unit's melee `jpt!` (35 to 45; `actors.txt` `unitmelee`) every 1.6 to 2.2 s with a shove, through the usual difficulty scaling. Further out it fires its fuel rod cannon from the tags (`hunter fuel rod`, its 75 to 40 blast), as before.

**Stealth Elites.** Variants with the `actv` active camouflage flag (the stealth Elites in a50, b30, b40 and c40, and d40's `floodcombat elite stealth unarmed`) are cloaked: actors see them only within about a fifth of their vision range (an eighth under super camouflage), as with the player's camouflage, and aim at them with extra error. They are drawn translucent through AssaultCube's translucent model path with a per-body opacity (`halomodelalpha`): a faint shimmer (about 0.05 to 0.13) that shows more of the body while the cloak flickers weaker, which it does for a second after the Elite fires or is hit (its cloak drops to about a third and recovers), the same fading the player's camouflage uses. Super camouflage (the stealth majors) hides a little more. A dead stealth Elite is visible. Spec-ops Elites have no camouflage flag in the Xbox tags and stay visible. Variants that cannot use ranged weapons (the energy sword Elites) now fight in melee with the sword's `jpt!` (151) times their damage modifier, at most one swing every 1.2 s.

**Flyers.** Actors whose `actr` has the flying flag (bit 21: Sentinels, the Monitor, Engineers) have no gravity, no jumping or landing and no ground snap (`halohovering` in `physics.cpp`; the player's movement is untouched); the brain sets their climb rate. They hold a height over the floor (a few times a second it traces the floor and ceiling under them: the retail BSP on retail collision, the cubes on stock geometry; over a drop with no floor in reach they hold the height they are at), fly straight to points instead of following the walking waypoints, and in combat hold 1.5 to 3.5 units over their target, keep their combat range and strafe across the target's line of fire, changing direction and height every 1 to 2.3 s. Killed, they fall. Sentinels fire their beam from the tags as before (a hitscan 1-point beam at 30 shots a second); the shielded variants have their `actv` shield (60). The brain's charge rule now reads the right `actr` flags (always charge; always charge or berserk while attacking): Sentinels and the Monitor no longer charge into melee, the Flood charges while attacking (all their squads start so), Infection and Carrier Forms always. **Enforcers** are a Halo 2 enemy: no Xbox Halo CE campaign cache has their tags, so there is nothing to place.

**343 Guilty Spark, Engineers, Keyes and Cortana.** The Monitor (`monitor` and `monitor_no_light`, kind 10) and the Engineer (kind 11) are new bodies: they fly, never fire or throw, and nobody targets the Monitor; its collision material has body multiplier 0, so it cannot be hurt (c20's scripts also set `object_cannot_take_damage`). c10, c20 and d40 have Monitor squads (c20 places them with `ai_place` and leads them with command lists), which it now follows in the air (`bsp0_monitor` to `bsp3_monitor` in c20). Engineers float in place and drift away from a threat; no Xbox campaign encounter places one (b30's cache carries the tags), so they only appear if a script spawns them. `tools/import_halo_campaign_actors.py` bakes `halo/monitor` (c20, its one idle clip), `halo/keyes` (a50's captain biped and graph) and `halo/engineer` (b30; batch 9: its graph has no node table of its own, so its tracks are read against the model's 25 nodes in order, as the device graphs are, and it is baked with its idle, move and alert clips instead of its bind pose); without them the Monitor draws as a Sentinel and the Engineer as a Grunt. The scripts cannot kill the Monitor (batch 9): `ai_kill` and `ai_kill_silent` of a squad pass over him, and `ai_erase` (c20 erases `bsp0_monitor` once the player moves on) and `ai_erase_all` remove him at once with no death, body or sound, as Halo's erase deletes the unit; other actors still die where they stand, as before. The captain and captain_ingame variants (a50's Keyes squads) draw as Keyes and fight as marines.

**Attached actors and story figures (batch 8, not verified in the game; `tests/test_ai_attach.py`).** `ai_attach <object> <squad>` in play now turns a scripted biped into an actor (`Scenario::attachActors` in `source/src/halo_script.cpp`): once nothing poses or carries it (no custom animation, recording or parent seat) and two ticks have passed since the attach, an actor of the squad's default variant (the `.hscb`'s version 9 squad defaults: a50's Keyes squads default to `captain_ingame`, its marine squads to the marine variants) spawns at the object's pose on the encounter's team, as a member of that squad (`ai_living_count`, `ai_actors`, migrations and orders reach it), and the scripted model is no longer drawn. An erased actor's live grenades go with it (`removebounceents`), since nothing may explode with a deleted owner. The object then stands for the actor: `unit_get_health` is the actor's health (-1 once it is dead or gone: a50's `game_lost_script` waits for Keyes's to reach 0), the unit commands, volume tests and `object_teleport` act on it, `ai_erase` and `ai_kill` kill it with its squad, and `object_destroy` (or `object_create_anew`) erases it at once with no death or drops (`haloerasebot`). A checkpoint keeps the living actor where it stands (a revert brings it back there, Continue too: the state block's optional `s attached` record) and one dead at the checkpoint stays dead after a revert. Where this applies: a50's `captain_keyes` and `free_marine_1` to `_3` after `ini_post_rescue`, its jailed marines once `unit_stop_custom_animation` frees them from their cell poses, `keyes_prison` never (he sits until the rescue destroys him), c10's `marine_suicidal`. A fix found on the way: `object_create` of an object that does not exist yet now makes it at its scenario placement, as Halo does; in a section started without an opening scene it was left at the origin (the object's pose was only set by a scene's start or by `object_create_anew`). Attaching inside a scene only records the squad, as before: a50's insertion marines and its final Hunters are attached in `cutscene_insertion` and `cutscene_extraction`, so they stay figures of those scenes. Limits: commands a script gives the object in the two ticks before its actor exists are not passed on (c10's `unit_set_maximum_vitality` and `unit_set_current_vitality` of `marine_suicidal` right after its attach do not reach the actor); a custom animation started on an object whose actor exists does not pose the actor (none of the retail scripts does this in play); actors, attached ones included, are not carried into the next section, so a50's Keyes stays behind in the cell block section when the player goes on to the hangar (his object is left alive, so `game_lost_script` does not fire).

Story figures, the scripted figures drawn outside scenes, are now flagged by the importer instead of picked by name (`story_figures` in `tools/import_halo_scripts.py`, `OBJECT_STORY_FIGURE` in the `.hscb`'s version 9 object flags): a biped not placed dead, or a character posed as scenery (a tag under `characters\`), that a gameplay script creates, or that a Call scene creates and leaves alive. Gameplay scripts are the startup and continuous scripts that are not scene cues and what they reach through static calls and `wake` without entering a cue script; the cue table is read from `source/src/halo_script.cpp` the way `tests/test_campaign_tables.py` reads it. The import prints each mission's list: a10 `keyesa10`, a30 `gunner`, a50 `captain_keyes`, `keyes_prison`, the freed, jailed and ship marines, c10 `marine_suicidal`, d20 `keyes_flood` (the Flood-infested Keyes, scenery, which the name rule drew too), d40 `cortana` (left on the bridge by `cinematic_bridge` until `chief_duck` destroys her) and `nipple_grunt`. The rule draws a flagged figure while no squad owns it, or while a custom animation poses it and no actor has taken it over (`keyes_prison` sitting in his cell, the jailed marines). Corpses placed dead (a30's `dead_marine_*`, b40's dump units, c10's bodies, d20's Grunts) and figures only scenes use are not drawn in play, and no scripted `monitor` object is drawn beside c20's Monitor actor. With an older `.hscb` the engine falls back to the old name prefixes (`keyes`, `captain_keyes`, `cortana`, `monitor`, not chips, effects or teleport effects). `ai_conversation_advance` was already bound; `recording_play` drives scripted objects, not actors, so the Monitor follows its command lists only; `unit_set_emotion` is still recorded without effect.

## Retail mission scripting

The importer reads the original scenario syntax datum array, strings, script and global tables, oriented trigger volumes, camera points, flags, chapter strings, AI squads and conversations. It keeps the compiled nodes and their validated handles. The script import includes 1,673 device placements, 119 BSP switch records, and 349 recorded input streams across the ten missions. Some Xbox voice tags carry no subtitle text.

The client executes script expressions at 30 ticks per second. It handles script calls, startup and dormant threads, conditionals, timing, globals, original volume tests, supported hostile placements, conversations and checkpoint requests. It keeps thread and global state during the ordinary section-to-section handoff. Cinematic entry and exit cues connect the retail script functions to the current route. Those scenes use the original camera data, scripted audio starts and waits, and retail BSP and object assets. Camera transitions use the observer's quintic interpolation for position, field of view and axis-angle rotation, carrying velocity and acceleration across waypoints. Compressed skeletal clips are sampled at the retail cadence. The in-game console command `halo_scripttrace 1` logs camera cuts and audio starts. `halo_script_status` lists the unbound commands reached in the current mission. Save and pacing commands are bound: `game_safe_to_save` is false while a Covenant actor is in combat, `game_save_cancel` drops a pending checkpoint, and `game_revert` kills the player. One HUD countdown (`hud_set_timer_time`, `show_hud_timer`, `pause_hud_timer`, `hud_get_timer_ticks`) follows the engine's escape deadline on the Maw run, so d40's timer script no longer wakes `endgame_cinematics` early. Tutorial prompts (`player_action_test_*`) finish on the matching input or after five seconds, and presentation-only calls (rumble, rasterizer, screen effects, `display_scenario_help`, `enable_hud_help_flash`) are no-ops. Scenes the scripts call in the middle of a section, the scripts' moves of the player and the remaining unbound commands are under Script scenes and player moves. Nav points and the HUD show and blink commands are drawn (see Nav points and HUD script commands). `tests/test_script_coverage.py` fails if a command used in a `sleep_until` or `if` condition has no handler.

## Script scenes and player moves

**Not verified in the game yet**: written and compiled while testing was on hold. `tests/test_mission_exits.py` (new) and items 12 and 13 of `tests/test_frontend_progress.py`, item 3 of `tests/test_script_coverage.py` and the title check of `tests/test_campaign_ending.py` are written but have not been run.

**Scenes the scripts call.** The cue table (`cues` in `source/src/halo_script.cpp`) has a fifth trigger, Call: when a gameplay thread calls a scene script that has a Call row for the section, the scene plays there and then, on the scene stage like any other cue, and the calling thread waits for it and carries on after the call (as in Halo, where `(if (cinematic_skip_start) (cutscene_rescue)) (cinematic_skip_stop) (ini_post_rescue)` runs the scene, then what follows it). The scripted objects are kept aside while it plays and put back after, except those the scene created or destroyed (d20's captain scene destroys the implants). A Call scene plays only when the script calls it, as in Halo: if the script is held up short of the call, the scene does not play. Call rows: a50's `cutscene_rescue` (section 4; it used to be that section's Exit scene, played when the player left the prison), b30's `cutscene_ledge` and `cutscene_shaftb_goal` (any section), d20's `cinematic_drop` (`cutscene_fall`, any section) and `cinematic_captain` (section 5; it used to be its Exit scene), and d40's `cinematic_bridge`, which now plays on the Autumn's bridge (section 2, BSP 1, called by `enc2_5`) instead of at the start of the engine room (section 5), where it used to be an Entry cue. The sections' engine interactions (a50's "Free Captain Keyes", d20's "Recover the Captain's implants" at their exits) still end those sections, now without a scene. A Call scene is not kept in the saved state: a save is never taken while one plays. Skipping a Call scene (Enter, or the QA walker) runs the rest of its script at once before it ends, with its waits passed over and `game_reverted` true (so a `cinematic_skip_start` part is passed over, as Halo's skip does by reverting), so what it does for the play after it still happens: b30's `cutscene_shaftb_goal` closes `shafta_lock_door` first and opens it later in the scene, and a skip that only ended the scene would leave it closed (log, if a loop holds it past 1024 passes: `Halo scene: <scene> did not run to its end when skipped`). A revert while a Call scene plays (not expected; the actors are held) ends it without handing the objects back or moving the player. Scripts named in the table are still never run inline by a gameplay thread; an Entry, Exit or Timeout scene still plays at the route's boundary and its call is passed over. Judgement calls: b40's `cutscene_insertion_b` is not cued, because it is not a camera scene (`camera_control false`, the first-person Pelican ride after `cutscene_insertion_a`), and b40's `cinematic_crev_ent_*` and `cinematic_ext_a_*` take no camera (dropship flybys); `tests/test_mission_exits.py` lists these and the other uncued camera scripts (a10's cryo exits `fast_setup` and `tutorial_action`, a50's `game_lost_script`, c10's `mission_control`, the uncalled placeholders) with the reason each plays as gameplay, and fails on any new one.

**Music and conversations across a Call scene (batch 8, not verified in the game).** A Call scene used to cut the gameplay music and conversations for good: every scene stops the script's sounds when it starts and ends. Now the looping sounds playing when a Call scene starts (`sound_looping_start` from gameplay, with their gain and alternate track) are started again when it ends, unless the scene stopped them (`sound_looping_stop`) or switched their alternate track (kept as the scene left it); and a conversation a scene cuts (any scene) counts as finished (`ai_conversation_status` 5), so a script waiting for it moves on instead of waiting at 2 for good. A loop restarts from its start (or its loop track), not where it was cut. A revert during a Call scene stops them again, as any revert stops the script's sounds. `tests/test_mission_exits.py` item 5 checks d40's bridge scene and a50's rescue (`qa_audio_state`, `qa_conversation_state`).

**a30's extraction.** The Pelican comes for the player at the last of the three marine sites they clear: its three exit scenes are variants of section 3's exit (rows with a vehicle, a volume and a site flag). The exit plays the variant whose Pelican the player boarded (`foehammer_cliff`, `_rubble`, `_river`), else the one whose site volume holds the player (`cliff_all`, `rubble_all`, `river_all`), else the one whose `*_hide_flag` is nearest the player (log: `Halo scene: <scene> chosen for the exit (<why>)`). The section's route ends at the river landing zone, so on foot that is the river scene, as before; the cliff and rubble sites lie outside section 3's map (the scripts' cliff and rubble extractions, which the player boards with E, now pick their own scene).

**The player moved by the scripts.** `object_teleport` and `object_set_facing` of `(player0)` (or the player list), and `volume_teleport_players_not_inside` (a player outside the volume, or a volume the scenario does not have such as `null`, goes to the flag), move the player in gameplay through `Scenario::placePlayer` and `haloplayerplace` (`halo.cpp`): to the flag's place on this section's map, facing its way, when the body fits there (retail collision: standing room on the mesh, as the recovery's safe spots; stock geometry: clear of the cubes and inside the map, on the floor of its cube column no more than 4 units below the flag), then through `haloplayermoved` like any other move that is not walking (log: `Halo script: player placed at <flag> (<command>)`). A flag that is not on a floor of the section's map (flags of another BSP fall outside it) leaves the player where they are (`... has no floor in this section's map (or the player is seated or dead); the player stays where they are`); so does a seated, dead or ending player. Inside a scene the player is off stage: the scene's last `object_teleport` or `object_set_facing` of `player0` is read from its script when it starts (following its calls, so a skipped scene ends the same way) and updated as it runs, and when a Call or Cartographer scene ends the player is put there. The entry shows the mission, section, difficulty and whether a checkpoint is saved, and is greyed out when there is nothing to continue. With a version 3 save the game resumes exactly at the checkpoint: Continue starts the section, skips its opening scene, loads the saved checkpoint into the in-memory checkpoint and reverts to it as a death would, so the mission script carries on with its threads, globals, doors and lifts, scripted objects, squads, nav points and HUD state as they were, the vehicles stand where they stood (a player saved in a seat continues in it), the weapons and equipment on the ground and the stock items are as they were, the scripts' limits on the player (`unit_set_maximum_vitality`, `unit_impervious`) hold, a running overshield or active camouflage keeps its time left, and a later death reverts there too. A save at a section's start (no checkpoint yet) holds the script carried in from the section before, and Continue resumes it at the section's start. Without a usable state block (a version 2 file, a save at the start of a mission's first section, or a block that does not fit, below) the mission script starts afresh on the section as before: its opening scene is skipped when resuming at a checkpoint, the player is put back at the checkpoint (with the engine's route stage and marker), and that spot becomes the checkpoint a death reverts to. On The Maw's run the escape countdown resumes with the time left at the section's start. All of this is unverified in the game; `tests/test_frontend_progress.py` (items 3, 4 and 8 to 11) checks it.

- **Mission select** lists the ten missions; those up to the furthest reached are playable (all of them once the campaign is beaten), the rest are greyed out as locked or not imported. Picking one asks for the difficulty. The in-game pause menu (**Halo Campaign**, Escape) uses the same list; the `halo_mission N` console command is not restricted.
- **Settings** and **Quit**. Escape with no menu open on the title screen brings the menu back.

The pause menu keeps Resume, Restart section, Mission select, Difficulty, Settings and Quit, and adds **Main menu**, which shows the title menu over the paused campaign (Escape returns to the game). Console commands behind the menus: `halo_title`, `halo_new_game <0-3>`, `halo_continue`, and the menu helpers `halo_can_continue`, `halo_continue_label`, `halo_unlocked`, `halo_mission_state <1-10>` (1 playable, 0 locked, 2 not imported), `halo_mission_title <1-10>`, `halo_difficulty_name` and `halo_progress_note`. `halo_campaign` (resume the furthest section from its start) is unchanged; tests and `play-macos.sh '-e...'` pass their own start command, which replaces `halo_title`.

The game is saved to `config/halo-progress.txt` in the profile at the start of every campaign section (section starts, section changes, restarts) and at every checkpoint, the engine's and the scripts' (`game_save`). Section selects and the Crash Site preview are not saved. The file is version 3, one record per line (`furthest`, `beaten`, `game`, `checkpoint`, `vitals`, `grenades`, `weapon` by retail tag path, `current`, `stock` for the fallback weapons without `weapons.txt`, then the state block) closed by a `check` line holding an FNV-1a hash of the rest. Version 2 files (the same without the state block) and version 1 files (`1 <mission> <section> [1]`) still load; a version 1 file's Continue starts the furthest section from its start.

The state block (`source/src/halo_state.h` for the record syntax) starts with `state <format> <mission> <section> <checkpoint> <.hscb hash> <section map hash> <records> <hash>`, the last two the number of records that follow and their own FNV-1a, so a damaged block is found even when the file's check holds. Its records are `s` (the mission script, `halo_script.cpp`): what the in-memory checkpoint keeps for a revert (every global by name, each thread by script name with its whole call stack, the scripted objects that differ from their defaults by object name, the living squad members by encounter, squad and start, every device group and device by object name, the external globals, the objective and help text, nav points, the HUD parts hidden or blinking, the chapter and the tick) and what the scripts set on the AI and a revert leaves alone (actor lists, `ai_link_activation`, migration targets, the platoon rules that fired, `ai_grenades`, the HUD timer); `v` (`halo_vehicle.cpp`): each vehicle of the checkpoint by vehicles.txt type and scenario object, its pose, motion, script settings, gun, safe spots and the player's seat (other riders and times in milliseconds are not kept); `w` (`halo.cpp`): the weapons and equipment on the ground (by tag path, scenario object and flags) and the stock items' spawned flags; `p`: `unit_set_maximum_vitality` and `unit_impervious` on the player and the powerups' time left. A save at a section's start writes only `s` and `p`, and only when the script was carried in (a section opened by the one before it, or continued); its opening scene ends first. Text is escaped so a record is one line; text and object pointers are written as offsets and indices; thread frames are the `.hscb`'s node datums. Continue checks the block before anything changes: its header, count and hash; that it is for the saved section; that the loaded `.hscb` has the hash it was saved with (frames mean nothing in another one); that every name matches the index it was saved at, every table has the size it had, and every frame's node exists. If any of that fails, the script restarts on the section as before, and the log (`Halo: The checkpoint's mission script state could not be restored; the script restarted on this section (<why>)`), the title menu's header and the pause menu's header warn about it; the Continue entry already says `(scripts changed: the section's script restarts)` when the `.hscb` on disk has another hash. If only the section map (`.cgz`) changed, the script's state is kept and the vehicles and ground items go back to their placements, with a warning. A file is expected to hold a few hundred kilobytes, perhaps a few megabytes late in a long mission (not measured; it is read up to 32 MB). Each save writes a temporary file, moves the previous file to `halo-progress.txt.bak` if it is valid, then renames the new one into place. On launch a progress file that fails its check is moved to `halo-progress.txt.corrupt` and the backup is restored and rewritten; the log (`campaign progress was corrupt ... restored from the backup`), the title screen and the title menu's header warn about it. With no usable backup progress is reset, with the same warnings. A save interrupted between its two renames is recovered from the temporary file.

Loadout persistence also applies within a session: finishing a section carries what the player carries into the next section of the same mission (Halo's sections are BSP switches), and a revert before the section's first checkpoint, or Restart section, returns to the loadout the player brought into the section rather than the starting one. A new mission (and a section started on its own) starts with the mission's player starting profile (batch 8, Retail weapons: a10 unarmed), or with the default assault rifle, pistol and two frags with an older `.hscb`. An empty slot is saved as `empty <slot>`.

**Optional state records (batch 8, not verified in the game).** The state block's `s` records may also hold, after the allegiances: `attached` (an actor `ai_attach` made of a scripted object: object, encounter and squad by index and name, suspended, script flags, whether it is dead, its variant and where it stands), `board` (the script vehicles the player may board: a30's extraction Pelicans made enterable, which the state used to drop, so after a Continue a30's seat tests fell back to "boarded"), `boarded` (the vehicle and seat the player was aboard at the checkpoint, and where they got in; a revert or Continue puts them aboard again) and `gain` (the 51 sound class gains, a fade in progress as its target: c10's music fades survive a Continue). Also `attaching` (review fix): the scripted objects attached in play whose actor does not exist yet (a50's jailed marines, posed in their cells until the rescue), so that after a Continue they still become actors when freed; a revert likewise puts back the attaches as they stood at the checkpoint (an attach made after it is undone with the script, one waiting before it keeps waiting) and clears the retry of a spawn that found no floor. A save without them loads with their defaults; an engine from before them refuses a save that has them (unknown record) and restarts the script on the section. Not added, on purpose: c40 section 4's Banshee of the engine's own needs no record (a checkpoint's vehicle list already holds it, and a Continue at the section's start makes another, as the section's start does); the EMP stun and the fraction of a health point exact hits leave over are under two seconds and under one point.

Limits: a save during a cutscene keeps no script state. Actors come back at their squad starts, as after a death revert (not where they stood). A revert after Continue at a checkpoint clears the overshield and camouflage, as any revert does; Continue at a section's start makes the carried script the state a death before the first checkpoint reverts to, as a live session now does too (Script scenes and player moves). Re-importing the scripts (`import_halo_scripts.py`) changes the `.hscb` hash, so saves made before it continue with the script restarted. ## Nav points and HUD script commands

**Not verified in the game yet**: written and compiled while testing was on hold. `tests/test_nav_points.py` is written but has not been run.

The mission scripts' nav point commands are bound: `activate_team_nav_point_flag <type> <team> <flag> <offset>` and `activate_team_nav_point_object <type> <team> <object> <offset>`, the per-unit `activate_nav_point_flag` and `activate_nav_point_object`, and the four matching `deactivate_*` commands (single player: the team or unit is not checked). A point is a cutscene flag or an object (it follows the object), raised by the offset in Halo world units; activating the same flag or object again replaces it. Nav points are saved with each checkpoint and restored by a revert, carried across sections within a mission and cleared when the mission script starts afresh. `source/src/halo_hud.cpp` draws them with the retail waypoint arrows: `tools/halo_hud.py` now exports the HUD globals' `hud_waypoints` bitmap and its ten arrow types (name, colour, opacity, on-screen, off-screen and occluded sequences) as `waypoint` and `arrow` lines in `packages/halo/hud.txt` (re-run `python3 tools/halo_hud.py "$maps"`; the bitmap ids of the other sheets shift, and the exporter now compares page contents so the copied textures follow). A point on screen gets the type's on-screen marker in its colour (blue for `default`, red for `default_red`); a point off screen or behind the view gets the off-screen arrow on the screen's edge, turned towards it. `hud_show_health`, `hud_show_shield`, `hud_show_motion_sensor` and `hud_show_crosshair` hide and show those parts of the retail HUD (and of the fallback HUD), and `hud_blink_health`, `hud_blink_shield` and `hud_blink_motion_sensor` flash them, as a10's cryo tutorial does on Normal (it hides the health, shield, motion sensor and reticle and reveals each in its lesson). The state is saved with checkpoints and reset when the mission script starts afresh. `hud_set_objective_text`, `hud_set_help_text` and `show_hud_help_text` were already bound. `show_hud` (the chapter title scripts) and `display_scenario_help` stay no-ops.

The retail reticles now hang from their registration point measured from the sprite's own corner (as the exported sheets store it), not from the page's; reticles on combined sheets whose sprite is not in the page's top-left corner were drawn off centre before. Also unverified in the game.
