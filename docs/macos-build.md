# Build Halo in AssaultCube on macOS

The engine source comes from AssaultCube Lockdown Edition v1.3.0.2, commit `1ece5af7533983bb8f827616381d282470793d90`. Engine and ENet notices are in `source/`. Stock data is read from a local AssaultCube RC1 release. The ten Halo missions, viewmodels, characters, compiled mission scripts, cinematic geometry and audio are generated from expanded Halo CE Xbox map caches. [AssaultCube v1.3.0.2](https://github.com/assaultcube/AC/tree/v1.3.0.2)

## Dependencies

Install Apple's command line tools, Python 3.9 or later, CMake, and the Homebrew formulae `sdl2-compat`, `sdl2_image`, `libvorbis` and `libogg`. The cinematic audio importer uses FFmpeg. The client uses the system OpenGL and OpenAL frameworks. `CMAKE_PREFIX_PATH` can point CMake at libraries outside the default Homebrew prefix.

```bash
brew install cmake sdl2-compat sdl2_image libvorbis libogg ffmpeg
```

Set `AC_ASSET_ARCHIVE` to the original `AssaultCube_v1.3.0.2_LockdownEdition_RC1.tar.bz2` file. The scripts also look for it in `~/Downloads`. The staging script checks its SHA-256, extracts game data and retains the bundled license in `build/runtime/docs/license.html`.

## Import, build and play

Run from the repository root with the directory that contains the expanded North American Xbox Halo CE 1.0 maps. Halo3DS's prepared `halo-source` directory has this layout. The campaign import needs all ten mission caches; the asset library also imports any multiplayer and menu caches in the same directory.

```bash
maps="/path/to/halo-source"
./scripts/import-macos-assets.sh "$maps"
./scripts/package-macos.sh
```

Open `build/Halo in AssaultCube.app` in Finder; it opens on the title menu (see Title menu and saved games). The app includes the staged data and converted files from `packages/`. `package-macos.sh` copies the non-system dylibs (SDL2, SDL2_image, Vorbis, Ogg and their dependencies) into `Contents/Frameworks`, rewrites their install names to `@executable_path/../Frameworks`, ad-hoc signs everything and fails if any `/opt/homebrew` path remains, so the app can be moved to another Apple Silicon Mac. It always verifies the full 55-section import (all `.cgz/.cfg/.mesh`, the `.hcol` files of the retail-collision missions, driven sections included, the ten `.hscb` and the weapon, equipment, actor and vehicle tables) and exits non-zero if anything is missing; pass `--partial` for a development package that only needs the Crash Site files, and set `HALO_PACKAGES_DIR` to package another asset directory. It also runs `scripts/check-no-retail.sh`, which fails if a retail-derived file is tracked, staged or not ignored (everything under `packages/` is ignored except `maps/halo_a30.cfg`), and refuses a `build/macos` configured with `HALO_SANITIZE=ON` (Robustness, sanitizers and CI). Licences ship in `Resources/licenses`; see `NOTICE.md`. Run `./scripts/build-macos.sh` and `./scripts/play-macos.sh` for source development. The campaign importer supports `--mission` and `--part` for focused map edits, writes each section's route metrics beside its map, and with `--metrics-only` writes only those (Route metrics). The script importer supports `--mission` and can regenerate the cinematic BSP meshes and models with `--rebuild`. Run `python3 tools/import_halo_scripts.py "$maps" --mission a10` before repackaging to upgrade an existing Autumn flyby mesh.

`build/retail-assets/catalog.json` indexes the local development library. It records every cache and tag, all BSPs, scenario placement tables, animation tracks, and looping sound definitions. The library copies the original caches into `sources/` and exports first-person and static models, full BSP meshes and collision, bitmap PNGs, and sound variants. Bitmap exports include cubemap faces and volume slices; P8 bump images preserve palette indices. WAV assets preserve the original Xbox sample encoding. The catalog records conversion gaps, and the copied caches retain the original data for future work. The campaign app uses its own converted media; the multiplayer caches and the original `ui.map` menu are in the library only (multiplayer and the retail menu are out of scope, NOTICE.md). Rerun only the library with `python3 tools/import_halo_library.py "$maps"`; add `--rebuild` to regenerate converted assets.

The Silent Cartographer uses retail collision across all three sections. To update an existing campaign install, regenerate the maps and script projections, then package the app.

```bash
python3 tools/import_halo_campaign.py "$maps" --mission b30
python3 tools/import_halo_scripts.py "$maps" --mission b30
./scripts/package-macos.sh
```

The original structure collision surfaces handle movement, weapon traces, and bot sight. Follow the path from the beach to the facility, use the Cartographer terminal, and climb back to the surface. Press **E** near the Pelican's rear ramp once it reaches the landing zone. The adapted entry leaves the security door open so the route starts at the descent.
To launch that section directly, run `./scripts/play-macos.sh '-ehalo_section 4 2'`.

### Retail collision for other sections

The engine plays any section on the original structure collision when `packages/maps/<section>.hcol` exists and loads (`Halo: loaded N retail collision surfaces for <section> (M static machines)` in the log); a missing file means stock AssaultCube geometry, and a file that fails validation is reported (`retail collision unavailable`) and also falls back to stock geometry. `tools/import_halo_campaign.py --collision validated|all|none` chooses the sections that get one: `validated` (the default) covers the missions in `VALIDATED_COLLISION` (a10, a30, a50, b30, b40, c10, c20, c40, d20 and d40) except the sections in `STOCK_SECTIONS`, which keep stock geometry (and need no `.hcol` in `package-macos.sh`); `all` writes every section, `none` removes them. For those sections the importer also

- projects each section's BSP with that section's own projection (b30's return reuses section 1's, which is why `halo_b30_03.hcol` is identical to `halo_b30_01.hcol`),
- bakes the scenario machines that never move (bulkhead frames, consoles, a10's jammed bulkheads, which the mission script creates) into the `.hcol` as their real collision polygons, listed in a `DEV1` trailer so the engine stops colliding with their coarse boxes; machines a script switches to a `door_off` permutation (a50's cell doors) keep the engine's removable box; machines that move only in a cinematic (`CINEMATIC_STILL`: c20's `index_platform`) are baked in their first pose,
- treats a closed one-sided door (it opens only for a player behind it) walked into from the front as a door to wait at if a script makes it two-sided or opens it, and as a wall otherwise,
- plans the walkable route, spawns, markers and items on floors with room for the body (walls, shelves, railings and invisible stair ramps included), routes round open door panels, crouches through crawl spaces, jumps low obstacles and gaps, waits at a door only if a script opens it and there is no other way (doors that scripts only close, and those in `NEVER_OPEN`, are walls), walks through the objective volumes the script waits for, or up to a control it waits for the player to use (`SECTION_OBJECTIVES`, which the section's projection also covers), and starts a section past the door its entry script shuts behind the player,
- goes round the vehicles parked in the section when it starts (`VehicleBlocks` in `tools/import_halo_campaign.py`), as the engine's bodies collide with them: the box `source/src/halo_vehicle.cpp` gives the vehicle (the retail model's length, a width centred on its axis and its height above the floor, at the section's scale) at the placement's map cell and heading, widened by the body and the walker's drift, from 0.25 units below the retail point to its top (a body within 0.42 AssaultCube units of the top stands on it). Placements a script creates (not-placed flag 1: most of a50's turrets, d40's trench jeeps, b40's `crev_ent` turrets) are not there when the walk passes and are left out, as are those no difficulty places; turrets, Ghosts, Wraiths, Banshees and Warthogs all count. A jump may not pass through one, and actors, weapons and equipment are not put inside one. The importer lists each walked section's obstacles (`route avoids parked vehicles ...`),
- treats lift platforms (b40's `lift_a` to `lift_d`, c10's `lift_a`, `lift_b` and `lift_d`) as something to stand on but not walk through, and can route a lift ride: a `SECTION_OBJECTIVES` control followed by the retail point where the ride sets the player down,
- treats a closed door that a script destroys (c10's `post_helmet_door_3`, replaced by a bashed-in door after the x50 scene), or whose device group a script opens (c20's floor doors, `device_group_set floor1_door1 door_open`), as a door to wait at, not a wall,
- never jumps through a sealed door or an open door's panels (door panels are not in the BSP, so the jump test missed them); a jump over a scripted door stays free, as a10's cryo jump tutorial needs. The next a50 import changes `halo_a50_02.route`, which jumped through `gravity_door_lr`'s open panels; the other validated routes are unchanged,
- walks off a ledge onto a floor further down than a jump drops only in the sections listed in `LEDGE_DROPS` (d20 sections 2 and 3, up to 3 and 2.6 units), at the cost of a 300-step detour, so other routes are unchanged; a section whose exit volume hangs in a shaft past the last floor (`EXIT_FALLS`: d20 section 1) ends its route with one more step over the shaft,
- in the missions in `UNGROUPED_DOORS_SEALED` (d40), treats a closed unnamed door with neither a power nor a position group as a wall: no script names it and nothing drives it, and a manual or unpowered door does not open on approach. Elsewhere such doors still count as doors to wait at, as the routes were planned (and a10's walked); switching a mission over needs a re-walk,
- reports the scripted doors a route waits at (including those a jump passes over), an objective it cannot reach (`no route to <volume>`) and a route that ends outside its exit volume (`WARNING route ends outside its exit`),
- walks c10's light bridges as floor once extended (`LightBridges` in `tools/halo_collision.py`: flat machine panels that slide out over a pit; the extended pose is the end of the animation whose panels join into one strip). Stepping onto a bridge that starts retracted costs as much as a scripted door, and is allowed only if a script extends it (`flicker_bridge` moves `bridge_c`) or one of its controls is within reach of the step before; `bridge_a`, whose only control is on its far side, cannot be crossed from lift_a's side. Bridge decks are kept out of the native cube floor, so actors, items and weapons are not placed on them,
- for the sections in `LIFT_RIDES` (b40 section 6, c10 sections 1 and 4, c20 sections 1 to 3, d40 section 5) writes one more route row on the lift's deck: beside the lift's control when one of the lift's controls is within reach of the deck (the walker uses it there to send the lift), else at the deck's centre (the Library's platforms rise once the player stands on them, d40's elevator once enc5_3 holds every player), with the lift position at which the deck is at that landing. The row is in the route file only; spawns, markers and items stay on retail floor,
- uses a control the script waits for (`UseControl` in `SECTION_OBJECTIVES`: the walker presses use until a named machine stands at a position) and shoots a damage target (`ShootTarget`: the route walks to the nearest standing spot from which a target is in sight, the eye 4.5 units above the feet, through the structure collision (two-sided surfaces included, as shots see it) and the machines in the pose the control left them, and only through the space the opened machine left; that machine's new pose is a wall for the walk there and its old one is not). A target no walkable spot sees is reported (`WARNING no route to sight of ...: the walker cannot shoot ...`) and the walk goes on without it,
- in the sections in `DOOR_WAITS` (a10 sections 5 and 6) writes a row of its own on the last step before each scripted door the route waits at, so the walker waits there (inside the door's opening radius) instead of backing off and retrying (`tunnel_door_2` in section 5; `cryo_door_2` and `cryo_door_1` in section 6). Only the route files change (a row is added after the step it stands on); the section maps are byte for byte as before. To go back, empty `DOOR_WAITS` and re-run `import_halo_campaign.py "$maps" --mission a10 --part 5` and `--part 6`,
- in the missions in `FLOOR_LEAVES` (c10), walks over a door's leaves folded flat on the floor (`floor_leaf` in `tools/halo_collision.py`: a panel of a door, device kind 0, whose top in that pose is at most 0.25 units above the door's base and which is at most 0.3 thick). c10's interior doors (the BSP 3/4 doorway's `bsp3_device_bsp4_device_1` to `_3`, BSP 4's `bsp4_device_12` and `_17`, BSP 1's and 2's doors of the same model) fold their lower leaves into the doorway when open, 0.05 to 0.23 units proud of the floor, more than a step at the indoor scale; Halo's biped walks over them, and the engine now does too (`Scenario::collideDevices` skips such panels for bodies; shots still hit them). The other missions' routes keep every panel solid, as they were planned and walked; the engine rule applies everywhere, where it only lets bodies through where the routes never go (a static scan of the retail tags finds such panels only on c10's doors: no other mission's door, kind 0 and not a lift, has a panel within those limits in any frame). None of c10's current routes (sections 1, 2, 4 and 7) crosses such a leaf, so their routes and maps are byte for byte as before; the leaves matter to sections 5 and 6, which stay stock for other reasons (below). To put c10 back, empty `FLOOR_LEAVES` and re-run `import_halo_campaign.py "$maps" --mission c10`,
- writes the route (`x y z [flags [device@position [ax ay az]]]`, flag 1 crouch, 2 jump, 4 the first step after a lift ride, 8 a walk off a ledge, 16 a lift's deck row, 32 call the lift from the landing (no script moves it) or use a bridge's control, 64 send the lift from the control on its deck, 128 a step on a light bridge that has to be extended, 256 use the control in reach until the machine named stands at the position, 512 shoot the damage target named down to the health given, at the aim point in the last three columns, 1024 wait at the door named until it is open that far; 256, 512 and 1024 rows repeat the step row before them) to `packages/maps/<section>.route` for `tests/test_retail_collision.py` (`tests/test_traversal_routes.py` checks the lift, bridge and action rows).

A scenario may give several trigger volumes one name (b40 has a `bsp 11,2` and a `bsp 2,11` at each of the c1 tower's two doorways). `SECTION_ANCHORS`, `TRANSITIONS` and `SECTION_EXITS` name the n-th of them `<name>#<n>`, in scenario order; a bare name is the last for anchors and the first for exit volumes. In the engine a BSP switch volume that holds the player when a section starts fires only once the player has left it, and is ignored for the whole section when another volume switches to the same BSP (the doorway the section was entered by).

### Falls, wedges, lifts and light bridges

None of this has been verified in the game yet: it was written while testing was on hold. `tests/test_retail_recovery.py`, `tests/test_traversal_routes.py` and the lift and bridge walks of `tests/test_retail_collision.py` (`PENDING_WALK`) check it once testing resumes.

- Falls out of the world. On retail collision a body can fall through a hole or seam in the structure, which the stock cube grid never had. The engine (`updateRecovery` in `source/src/halo.cpp`) keeps the last eight retail floor spots the player stood on, at least 2 units apart (only real structure floor counts: not a lift deck or a light bridge, which move or vanish). A player whose feet are more than 8 units below the section's mesh, or who has been in the air for two seconds with neither structure nor device below down to that depth, is put back on the newest of those spots that is still clear (`Halo recovery: fell below the retail collision, player put back at x,y,z`, or `fell out of the world`). A second recovery within five seconds goes one spot further back. If none is clear, the player dies and reverts to the checkpoint as usual. Actors (enemies and allies) whose feet fall below that depth die, as in Halo. Ordinary falls, into a pit with a floor, or d20's jump into the shaft its exit volume hangs in, never reach that depth or that airtime over nothing, and the checks do nothing on stock geometry, during cinematics or once a section is complete.
- Wedges. A player whose body overlaps the structure by more than 0.1 units or is inside a device's box (a door or a lift deck closing on them) for 0.75 s, or who has been in the air without moving at all for 1.5 s (caught in a crease too steep to stand on), is moved to the nearest clear retail floor within 3 units (`wedged in the collision`, `stuck in mid-air`), or failing that to a safe spot as above. A player wedged before standing on any retail floor since the last move that was not walking (a spawn, a revert to a checkpoint on a lift deck, a teleport) is not reverted, which would put them back in the same place and loop: they are left where they are (`no safe floor since the checkpoint, player left in place`) and checked again five seconds later. A spot inside a vehicle's footprint (one parked there since) is neither recorded nor used. None of these checks run while the player is in a vehicle seat; the vehicle has its own stuck recovery (see Vehicles). A player thrown out of a vehicle onto it, with no room for the body beside it, whom these checks find wedged or falling within 15 s, without having taken a seat since, is put back in that seat instead (not after the vehicle itself fell out of the world), the vehicle righted where it lies or moved to where it fits (`Halo recovery`'s reason, then `player put back in the Warthog at x,y,z`): in the Maw's run the driver has never stood on retail floor, and this used to log `player left in place` every five seconds. Moves that are not walking reset this recovery (see the next item).
- Moves that are not walking. Every move of the player other than walking goes through one helper, `haloplayermoved` in `source/src/halo.cpp`: a spawn or revert, Continue, a section start (BSP switches end a section, so this covers them), the end of a cutscene (the Cartographer's handoff moves the player; every scene's end is treated the same), getting into a vehicle seat (the scripts' `vehicle_load_magic` and `unit_enter_vehicle`, a revert or the Maw's escape seating the player, a reclaim) and out of one (beside it, or thrown onto it), and every QA hook that teleports the player (`tests/native/*.inc`, except `qa_retail_recover`, which stands in for a fall or a wedge). It drops the safe spots recorded before the move, so the recovery never puts the player back on a floor from before a teleport, restarts the wedge and stall timers, and starts a one-second grace in which the wedge and stall checks do not count (the falls are still checked): a wedge right after a move is nudged after 1.75 s instead of 0.75 s. Getting into a seat keeps one safe spot, the retail floor the player got in from: when the vehicle falls out of the world with no safe spot of its own, the driver goes there (`halorecoverplayer`) rather than dying. With `halo_scripttrace 1` each move is logged (`Halo moved: <why>, N safe floors dropped`). The mission scripts' player teleports (`object_teleport` of the player, as in d20's captain scene and d40's bridge) are still not performed, so they do not move the player. Not verified in the game: `tests/test_retail_recovery.py` checks it (`qa_halo_moved`).
- Lifts. Everyone standing on a lift's deck is carried with it: the player, allies and enemies, on retail collision as on stock geometry. On a rising deck a body counts once any part of it is over the deck, as the device collision stands it there, so the deck no longer lifts into someone on its edge and wedges them (only the player whose centre was over the deck used to be carried). A descending deck carries only the bodies whose centre is over it, so someone standing on the landing beside a flush deck is not dragged down through the landing's floor. A lift's deck at rest may stand higher above its landing than a step: the Library's platforms are 0.38 units up at the bottom of their shafts, 2.6 units at floor 1's scale, against a 1.26-unit step. A grounded body may step onto a lift deck from up to 0.45 retail units below its top (`Scenario::liftBoard`); nothing else changes the step height. The device's collision is its boxes in the current animation pose, so it moves with the lift.
- Light bridges. A light bridge is a machine whose panels slide out over a pit; the engine collides with each panel's box in its current pose, so an extended bridge is floor and a retracted one leaves the pit open. A bridge that retracts under the player (c10's flickering `bridge_c`) drops them into the pit; if the pit has no floor, the fall recovery puts them back on the last floor they stood on. The route planner models them as above (`LightBridges`).
- The QA walker (`tests/native/retail_qa.inc`) boards, calls and sends lifts at deck rows, waits two rows short of a light bridge until it is extended, and after a recovery carries on from the nearest route row behind it. See `tests/README.md`.

## Presentation

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold; nothing of it has been seen or heard. `tests/test_presentation.py` is written but has not been run. The code is `source/src/halo_fx.cpp` (`halo_fx.h`); apart from the melee lunge (below), none of it changes the game's state (no damage, no movement, no script results).

```bash
python3 tools/halo_weapons.py "$maps"                    # zoom-in, zoom-out and loop sound roles
python3 tools/halo_vehicles.py "$maps"                   # engine, crash and suspension sounds
python3 tools/halo_effects.py "$maps"                    # packages/halo/effects.txt
python3 tools/import_halo_audio.py "$maps/a30.map" .     # decodes them; tags/classes.txt
```

`import-macos-assets.sh` runs `tools/halo_effects.py` before the audio import and `package-macos.sh` requires `effects.txt`. All of it is generated and git-ignored. The new `sound` roles and lines are skipped by older games and the tables keep their formats (weapons.txt 3, vehicles.txt 2).

- **Script effects.** `tools/halo_effects.py` reads every `effe` tag a mission script names (the effect constants of `effect_new` and `effect_new_on_object_marker`, and d40's effect globals such as `explosion_large`; 20 tags) and writes, per effect, a kind (explosion, burst, smoke or glow), a size (1.6 for the tags' large particle systems, 0.6 for small ones and grenades), its first light (radius, colour, duration), the area radius of its strongest `jpt!` part and its first sound. `effect_new <effect> <flag>` draws it at the cutscene flag's place in the section, `effect_new_on_object_marker <effect> <object> <marker>` at the object (its origin: markers are not resolved). AssaultCube's particles stand in for the tags' particle systems: an explosion is a fireball (three for the large ones), sparks, smoke and a flash, and knocks the camera within three times its radius; a burst is sparks and a flash; smoke is smoke; a glow a flash and a few plasma sparks. The effect's light lights stock geometry only (the retail mesh keeps its lightmaps). The tags' particle systems, decals, debris and damage are not converted: Halo's `pctl` and `part` tags carry their own shaders, bitmaps and physics, which AssaultCube's fixed particle types cannot show without a particle renderer of their own, and the damage is left out on purpose (d40's escape sets explosions off along the route, and with the flags projected onto AssaultCube's maps a damaging one could kill the player where Halo's would not). In a scene, whose flags and objects are in the scene's frame, an effect only plays its sound, unpositioned. An effect the table does not have still draws (an explosion when its name says so, else a burst; logged with `halo_fxtrace 1`).
- **Camera shake.** `player_effect_set_max_translation` (world units), `player_effect_set_max_rotation` (degrees: yaw, pitch, roll), `player_effect_set_max_rumble` (the controller's motors, 0 to 1: a fine fast tremble here), `player_effect_start <intensity> <attack s>` and `player_effect_stop <decay s>` shake the view; `player_effect_impact` and `player_effect_rumble` are a half-second knock. Vehicle crashes (the player's vehicle), the explosions above and grenade, rocket and other blasts within three times their radius knock the camera too. The shake moves only the rendered view (`transplayer` and the sky), never the player's yaw, pitch or position, and is smooth noise of the time (it does not draw on the game's random numbers); the player's shots still go where the shaken view's centre (the reticle) points, since the aim point is read from the drawn frame. It is capped at 8 degrees; `halo_shake 0` turns it off. A checkpoint revert stops the shake and clears the cinematic screen effects and the damage arcs (the reverted script starts its own again); the sound class gains are kept.
- **Cinematic screen effects.** `cinematic_screen_effect_start` turns them on and `_stop` clears them. `_set_convolution <iterations> <mode> <from> <to> <s>` blurs the view from one radius to the other (retail radius in 480-line pixels): the frame is copied once and laid back over itself in up to three rings of eight offset copies. `_set_filter <desaturation from> <to> <tint from> <to> <additive> <s>` with `_set_filter_desaturation_tint <r> <g> <b>` takes the colour out of the view towards the tint, approximated without shaders (a multiply towards the tint and a grey wash); `_set_video <mode> <intensity>` (c10) draws scan lines and a cold cast. They draw over the 3D view and under the HUD and the scenes' letterbox and fades; `halo_screeneffects 0` turns them off.
- **Flashlight.** **X** (`halo_flashlight`) turns it on and off. Its light is the cyborg's `characters\cyborg\flashlight_cyborg`: 6 world units of radius, full inside 20 degrees and none past 45. On the retail mesh it is a pass after the solid surfaces that adds each surface's own texture lit by a spot projected from the eye, fading to nothing at the radius; on stock geometry it is an AssaultCube dynamic light a little ahead of the eye. Actors and models are not lit by it. It drains over 60 seconds on and recovers over 30 off (an engine choice: the tags hold no flashlight energy), and the retail HUD's flashlight meter shows its charge while it is on. It goes off at a section start and when the player dies.
- **Damage-direction indicator.** A hit on the player from an actor, the shield's included (a hit the shield takes whole used to show nothing), draws a red arc round the reticle towards where the attacker was, in the world (it follows as the player turns), fading over a second; hits from about the same way renew one arc, up to eight. It replaces AssaultCube's own indicator in the campaign; `halo_damageindicator 0` turns it off.
- **Sound classes.** `sound_class_set_gain <class> <gain> <ticks>` fades every retail sound class whose name starts with the given one (`vehicle` is `vehicle_collision` and `vehicle_engine`, `ambient` the three ambient classes) to the gain. It reaches the scenario's sounds (music, ambience, dialogue: `tools/halo_effects.py` writes each cache's `snd!` classes, and the channels already playing follow the fade), the decoded tag samples the engine plays (weapon, grenade, equipment, vehicle and effect sounds: `tags/classes.txt` from the audio import) and the engine loops. AssaultCube's own samples (footsteps, the fallback weapon sounds) have no class and are not faded. The gains go back to 1 at each section start and on Continue (they are not in the progress file: a class the script had faded before the save plays at full gain until the script sets it again).
- **Vehicle sounds.** `tools/halo_vehicles.py` adds the tag's sounds to `vehicles.txt`: the engine loop (the first looping sound attached to the vehicle: `warthog_7_engine`, `ghost_lp`, `banshee_engine`, the Scorpion's `warthog_engine`, `wraith_eng1`, the turret's `c_turret2`), the crash (`jeep_hit_solid`) and the suspension (`warthog_suspension`, the Scorpion's own). The engine loops from whoever drives (a turret's while its gunner turns it faster than 15 degrees a second, held for a quarter second), its pitch rising with the speed, and stops when nobody does; the crash plays when a vehicle loses more than a third of its top speed in one step against a wall, a body or another vehicle, the suspension on a landing faster than 14 units per second down, at most one of them every 0.4 s.
- **Weapons.** Zoom steps play the weapon tag's zoom-in and zoom-out sounds (`weap` +408 and +424 after the item section: the pistol's, sniper rifle's and rocket launcher's `sniper_2x_zoom` and `sniper_10x_zoom`). A looping sound attached at a trigger marker is the weapon's `sound loop`: the flamethrower's `fire_ft` (its only firing sound) plays while the trigger is held and it can fire, and the plasma pistol's `charge` hum once a charge has built for 0.15 s.
- **Melee lunge.** A hostile actor in sight within 1.8 times the blow's reach (7.2 units) and 25 degrees of the aim takes the blow, and the player is pushed towards it by a velocity impulse that the floor's friction takes out (about 1.9 units travelled per unit of impulse, closing the gap to about 3 units), as an explosion's knockback is applied; the movement constants are untouched. `halo_meleelunge 0` turns it off; `halo_meleetrace 1` logs it.
- **Rocket launcher.** Its tube rides the right shoulder with its top above eye height; in AssaultCube's wider view (75 degrees vertical for the weapon, where Halo's view is 70 degrees horizontal) it filled the right of the screen. It is now drawn 0.5 units further right, 1 forward and 1.5 lower than its retail animation holds it. This is a judgement call made without seeing it: `halo_viewmodeloffset <right> <forward> <up>` changes the current weapon's placement in the game (no arguments prints it), for tuning, and the values belong in the table in `source/src/halo.cpp`.
- **Reticles.** Vehicle guns use their own retail reticles where the HUD tags carry them (the turrets, Warthog, Ghost, Scorpion, Banshee and Wraith guns all do). A weapon whose HUD tags have no reticle (the flamethrower, whose weapon HUD is empty) gets a plain one, a circle and four ticks in the retail blue (red on an aim-assist target), and shows its rounds or battery as text; without `hud.txt` a seat's gun gets the plain reticle too.

## Vehicles

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold, the vehicle fixes (bodies inside vehicles, shoving, stuck recovery, the escape taking over a scenario Warthog, lift decks, routes round parked vehicles) included. `tests/test_vehicles.py` (items 7 to 9 for the fixes), `tests/test_maw_drive.py` (item 6) and the parked-vehicle check in `tests/test_traversal_routes.py` are written but have not been run.

`tools/halo_vehicles.py "$maps"` (run by `import-macos-assets.sh` before the campaign import) writes `packages/halo/vehicles.txt` from the retail `vehi` tags and exports their models to `packages/models/halo/vehicle/<name>` (git-ignored, like everything under `packages/`). It lists six vehicles in a fixed order: the Warthog (a car), the Covenant gun turret (a fixed gun with a gunner seat), the Ghost (a hover craft), the Scorpion (a tank), the Banshee (a flyer) and the Wraith (a hover craft the player may not drive); see Enemy and flying vehicles. Each record carries the class, whether the player may drive it (format 2; the game still reads format 1 tables, giving their props a class from the retail motion kind), the drive parameters, the model's bounds, the seats with their markers and the vehicle weapon from `weapons.txt`. `package-macos.sh` requires the file. Without it the engine falls back to a built-in Warthog with the model the actor importer writes to `packages/models/halo/warthog`; a vehicle with no model is drawn as a wire box.

`tools/import_halo_campaign.py` writes each mission's scenario vehicle placements (the `scnr` vehicle block) of those six types into the sections whose BSP holds them, as `PLAYERSTART` entities with team 102: the type, the placement's not-placed flags, the scenario object index and the section scale. On retail collision they stand at their retail point and settle onto the floor; on stock geometry they go on the nearest raster floor. Placements the scripts create (`object_create`, not-placed flag 1) appear when the script creates them; the others appear at the start, except on the difficulties their flags leave them out of. Re-run the campaign import (all missions) to place them. Imported: d40's six parked escape Warthogs in section 6, a Warthog and a turret in section 7 and the two enc7_7 turrets in section 8; a50's 14 turrets; the Warthogs, Ghosts and Banshees of a30, b30 and c40; b40's turrets, Ghosts, Wraiths and Banshees (its Scorpion stands outside every campaign section); the turrets of c10 and d20. Pelicans, dropships, lifepods and cinematic props are left out.

`source/src/halo_vehicle.cpp` runs them:
- **E** by a seat's door gets in (the driver's door of a Warthog, its rear for the gunner's seat, a turret's gun); in a seat **E** gets out beside the door, or on the other side, behind, ahead or on top, wherever the body fits, and stays in when none does. A seat nearer than a weapon on the ground wins **E**. The HUD prompts `E  Drive the Warthog`, `E  Warthog gunner`, `E  Man the Covenant Turret` or `E  Flip the Warthog`.
- The Warthog drives with **W**/**S** (throttle, brake, reverse) and steers towards where the camera looks, as the retail Warthog does; **A**/**D** steer directly. `halo_vehiclesteer 1` steers with the keys only. The camera orbits behind with the mouse. Top speed is the retail Warthog's at the section's scale, and never below 36 units/s (the old escape pace, which the 3:00 timer was set for); grip is strong with some slide, it climbs and jumps off crests, pitches and rolls with the ground, and flips when it lands on its side or back or stands over more than 58 degrees. Upside down for 0.7 s it throws the driver out; **E** beside a flipped vehicle puts it back on its wheels. Running into actors at speed kills them. It is not the retail physics.
- The bodies are the retail vehicles' size at the section's scale. On retail collision the Warthog drives on four wheel traces and two chassis capsules against the structure and the machines (doors); on stock geometry on the cube grid (it steps up whole cubes as the walking body does). Bodies collide with vehicles (`halo_vehiclecollide 0` turns that off, for checking a route walk a placed vehicle blocks); the walking routes go round the parked ones (above).
- Bodies inside vehicles. ### Damage fidelity

Written while testing was on hold; nothing here has been run in the game (`tests/test_damage_model.py` checks it and has not been run either).

**The jpt! bounds.** A full-strength hit deals a random amount in the upper bound's range; a weakened hit at scale s deals `lower + (full - lower) * s`, the reading of Halo's damage formula used here (the community tag definitions describe the lower bound as what a scaled hit falls to; not checked against the retail executable). Scale comes from:

- **Range falloff.** An impact closer than the near end of its projectile's air damage range deals full strength, falling linearly to the lower bound at the far end and staying there (a far end of 0 means no falloff). From the tags: shotgun pellet 1.5-3 world units (18-25 down to 8), plasma rifle bolt 20-50 (12-14 down to 10), plasma pistol bolt 20-50 (16-20 down to 10), Ghost and Banshee bolts 20-50 (10-14 down to 10), covenant turret bolt 0-100 (12-14 down to 8), Warthog chaingun 0-100 (16-24 down to 16). The assault rifle (5-15), pistol, sniper rifle, needle, the charged plasma bolt (5-20) and flame are flat (lower equal to upper), so their range does not matter. The distance is the shot's travel (hitscan: muzzle to impact) in Halo world units. Falloff applies to impact damage only, not to the blast of an exploding projectile (rockets, fuel rods, mortars, the Scorpion shell), and to the player's and the actors' shots alike.
- **Blast edges.** Area damage is full inside the inner radius and falls to the lower bound at the outer radius; beyond the outer radius there is none, so the blast steps from the lower bound to nothing at its edge. Grenades: frag 1.5-2.5, plasma 0.5-2.0 world units, both 120 at the centre and 80 at the edge. Exploding projectiles now use their inner radius too (rocket 0.5-2.0, 300-330 down to 80; fuel rod 0.5-1.5, 75 down to 40); before, they fell to none at the outer radius. The `jpt!` cutoff scale is zero in every campaign tag and the AOE core radius is not used.
- **Melee** keeps the full-strength roll (50-60; the flamethrower 70-80). The engine has no melee lunge, and the melee tags' radius bounds are 0.5-0.5, which gives no scale between full strength and the lower bound, so there is no sensible mapping for the lower bound (40). Every weapon's melee carries side effect 2, "lethal to the unsuspecting" (Halo's kill from behind), which is not modelled.

**Grenades by thrower.** The player's grenades roll the retail full-strength range (120, and a stuck plasma grenade adds its attached 120). Grenades thrown by actors roll from the lower bound, 80 to 120, the balance they had before the `jpt!` layout correction, for the blast and a stuck plasma grenade's attached damage alike; with the edge falloff their blast deals 80 to 120 anywhere inside the outer radius. Against the player's 150 of shield and health on Normal an actor's frag at the player's feet deals 80 to 120 (Heroic 104 to 156, Legendary 136 to 204), and at the edge of its blast 80 (it dealt nothing there before).

**EMP.** Side effect 3, carried by the plasma grenade's blast and attached damage and by the plasma pistol's charged bolt (and the needle supercombine, which is not modelled): the shield the hit reaches is drained to nothing after the hit is taken, the player's (its overshield layers too, ending the powerup) and any actor's (Elites; Jackals' shields count too). The hit itself is absorbed as usual, so EMP does not add damage to health. Vehicles inside a plasma grenade's outer radius, the one it is stuck to and one a charged bolt hits are stunned for 2 s (`HALO_EMP_STUN_MILLIS`; the tags' stun times are all zero, so the duration is the engine's): a vehicle's throttle does nothing (it coasts and steers; a hover craft does not strafe either, a Banshee sinks), whether the player or an actor is at the controls, and the seat's gun cannot fire, the player's or an actor gunner's. Charged bolts now stop on a vehicle's body; other shots still pass through vehicles. Stunning a vehicle is Halo 2's behaviour more than Halo CE's; it is here because it was asked for.

**Enemy fire.** Every actor shot now rolls the weapon's full-strength range (upper min to upper max), applies the range falloff, and multiplies by the variant's damage modifier (0.5 without one); halodamage then applies the difficulty and the vehicle cut. The amount stays fractional: `halohit` hands it to halodamage, the shield takes its exact share, and the health damage keeps the fraction to the next hit (per target), so a 6.5 bolt costs 6.5 points on average where the slot damage dealt 6 or 7. An actor's shot deals at least 1 point, the floor the integer slot damage had. That floor is the one retune: without it the Sentinel beam (1 x 0.5) would take twice as long to kill. The player's shots go the same exact way (their rolls are unchanged). `halo_damagetrace 1` logs every hit halodamage sees (`DAMAGE_TRACE`).

## Grenades, equipment and weapon audio

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold. `tests/test_combat_equipment.py` is written but has not been run.

`tools/halo_weapons.py` also writes `packages/halo/equipment.txt` (git-ignored like the rest of `packages/`) and adds `sound` and `ammo` lines to `weapons.txt`. The equipment table holds the globals' two grenade types (carried maximum, the thrown projectile's fuse, whether its material responses attach it to units, the detonation's blast radius and damage and a stuck grenade's attached damage, the throw and explosion sounds), every campaign `eqip` tag (its powerup kind and time, pickup sound and pickup model, and the weapons whose magazines take it as ammunition) and the interface's low-shield and low-health sounds. `package-macos.sh` requires the table. Without it the frag grenade falls back to AssaultCube's grenade and there is no plasma grenade.

- **Grenades.** **G** throws the selected type, **H** (`halo_grenade_switch`) switches to the other type when you carry some. Both counts show under the retail grenade panel (which shows the selected type), the selected one in brackets. The last grenade of a type switches to the other, and picking up a type when the selected one has run out selects it, as in Halo. Each type is carried up to its tag maximum (4). Frag grenades bounce and explode once armed (1.5 s after the throw) and 0.5 s after their first bounce; plasma grenades stick to the unit or vehicle they touch (a bounce off a body, or coming to rest against one) and explode 2 s after sticking or coming to rest. The blast is the detonation effect's `jpt!`: full damage inside its inner radius, falling to the lower bound at the outer and none beyond, blocked by walls; the unit a plasma grenade is stuck to also takes the attached damage. Actors' grenades roll from the lower bound (Damage fidelity). Damage to the player goes through the difficulty scaling like any enemy weapon. A grenade the player throws can hurt the player. The plasma grenade's EMP drains the shields it reaches and stuns vehicles (Damage fidelity).
- **Actors** throw their variant's grenade type (`actors.txt`; the Covenant and Flood Elites throw plasma, marines and human Flood frags; a variant that names no known type throws plasma on the Covenant side and frags on the human side), and drop the grenades they still carry (at most two) beside their body when killed, unless `unit_doesnt_drop_items` is set.
- **Scenario equipment.** `tools/import_halo_campaign.py` writes each mission's scenario equipment placements (the `scnr` equipment block) that lie on the route's floor as `PLAYERSTART` entities with team 103: the `equipment.txt` index, the not-placed flags and the scenario object index. Sections with retail equipment no longer get the old stand-in ammunition, health and grenade boxes; sections without any keep them. Placements the script creates (flag 1, for example b40's supply dumps) appear on `object_create`/`object_create_containing` and go on `object_destroy`; the difficulty flags (not on Easy, Normal or Heroic, Legendary following Heroic) leave placements out as for vehicles. A checkpoint saves what is on the ground; a revert restores it. Re-run the campaign import (all missions) and `tools/halo_weapons.py` before it. The standalone `halo_a30` crash site map keeps its stand-in items.
- **Pickups** happen by walking over an item that does the player good: an ammo pack adds its rounds to the carried weapon it belongs to (up to the weapon's maximum); a health pack restores full health; a grenade adds one of its type; the **overshield** fills the shield and charges two more layers over 1.5 s (three times the shield), which take damage first and drain over the powerup time (60 s); **active camouflage** lasts its powerup time (45 s) and fades over its last 3 s. Under camouflage actors see the player only within about an eighth of their vision range (two fifths for a second after the player fires), lose track of a player they were fighting after 4 s, and aim with extra error. The screen takes a faint tint and the HUD counts the camouflage down; the overshield shows as green, then red layers over the retail shield meter. Double speed and full-spectrum vision are not campaign pickups and stay on the ground.
- **Weapon audio** comes from the weapon tags for every campaign weapon the player or an actor fires: the first trigger's firing, empty (dry fire, and the overheat click of a Covenant weapon) and misfire effects, the second trigger's charged shot, and the first-person animation graph's sounds (ready, reload and empty reload, melee, the overheat, and the shotgun pump and rocket cycle played with each shot), plus the weapon's ammo pickup sound. Grenades play their throw and explosion sounds (and the plasma grenade its hiss), equipment its pickup sound, and the player hears the low-shield alarm while the shield is below a quarter and not recharging and the heartbeat while health is below a third with no shield. `tools/import_halo_audio.py` decodes every sound the two tables name from whichever campaign cache holds it to `packages/audio/halo/tags/` (`sound\sfx\weapons\needler\fire` becomes `tags/sfx-weapons-needler-fire.wav`); the flamethrower's firing effect has no sound of its own: its fire is the looping sound attached at its trigger marker (`sound loop`), held while the trigger is (Presentation). ## Actor AI

`tools/halo_actors.py` writes `packages/halo/actors.txt` from the campaign `actr` and `actv` tags: vision and hearing, firing range, rate and error, burst timing, combat range, target leading, grenades, vitality, shield-based hiding, panic chances, berserk thresholds and position hold times; format 2 adds each variant's unit team, unit melee and collision materials (Factions and special enemies). Run it after `halo_weapons.py`. `import_halo_scripts.py` then writes version 6 `.hscb` files. These add each encounter's combat positions, squad states and position-group masks, platoon rules, per-start variants and command lists, and the scenario's command lists.

The campaign ending is driven by the scripts. `game_won` on The Maw's last section, or the finale cue finishing that section, starts an ending: a credits roll over the level (Enter skips), `config/halo-progress.txt` marks the campaign beaten (`beaten 1`, with every mission unlocked and no game left to continue), and the game opens the title menu (**Halo**) over the level (until this batch it opened the **Halo Campaign** pause menu; the change is not yet verified in the game). `game_won` on earlier sections is ignored, because sections advance on their own. `game_lost` kills the player so the normal revert applies.

Campaign bots think with `source/src/halo_ai.cpp` instead of AssaultCube's bot AI. AssaultCube still handles movement, pathfinding and physics. Actors:
- notice targets inside their vision cone, or hear gunfire, after a reaction delay
- alert nearby squadmates
- take combat positions from their squad's groups for attacking, defending or pursuing
- fire in retail bursts and throw grenades
- hide when their shields are low, panic when friends or leaders die, and go berserk when badly hurt
- follow command lists.

Marine and crew encounters now spawn on the player's side and fight the Covenant and Flood. Platoon rules switch squads between attacking and defending as casualties mount. The scripts' AI commands work, including `ai_actors` lists, `ai_status`, `ai_living_fraction`, `ai_strength`, magic sight, follow and fight orders, `ai_migrate` to new positions, command lists and their status, and `objects_can_see_*`. Vehicle seat and boarding commands act on the engine's vehicles and on dropships and Pelicans (see Vehicles, and Enemy and flying vehicles); for other vehicles they are stand-ins. The AI, unit and object-state commands live in `source/src/halo_script_ai.inc`. `ai_berserk`, `ai_grenades`, `ai_allow_dormant`, `ai_maneuver_enable`, `ai_renew`, `ai_prefer_target`, `ai_follow_target_ai`/`_disable`, `ai_follow_distance`, `ai_braindead_by_unit`, `ai_free`, `ai_try_to_fight_nothing`, `ai_link_activation` (waking the linked encounter once one is alert), `ai_teleport_to_starting_location*`, and the migrations (`ai_migrate_by_unit`, `ai_migrate_and_speak`, `ai_attach` on an actor) change what the actors do; flags survive a revert. `object_cannot_take_damage`, `unit_impervious` and `unit_doesnt_drop_items` apply to actors and the player, `unit_set_current/maximum_vitality` set the player's health and shield (maximum shield 0 removes the shield) or an actor's fraction of spawn health, `unit_suspended` stops an actor thinking, and `object_set_permutation door_off` removes a cell door and its collision. `damage_object` and `damage_new` do not read the retail `jpt!` effects: names with guaranteed, doom, plummet or death kill, any other effect does 40 damage. Recorded but without visible effect: `unit_open/close`, `vehicle_hover`, `object_set_collideable`, `unit_set_enterable_by_player`, `ai_attach` and `ai_attach_free` on scripted objects, `ai_automatic_migration_target`, `ai_exit_vehicle` and `ai_vehicle_enterable_*` on vehicles the engine does not drive, `ai_allow_dormant` (no dormancy exists), `unit_set_emotion`, flashlight state and `ai_dialogue_triggers`. `(player0)` now evaluates to the player and `(player1)` to nothing. Balance has only been checked in short QA runs: enemies are accurate at close range.

Only living actors count towards the 128-actor cap on scripted placements; dead squad entries stay for `ai_living_fraction` and to stop a killed start respawning. The Flood life cycle is not scripted: a dying Carrier Form bursts into 4 to 8 Infection Forms, Infection Forms walk to a fallen marine or Elite (bodies last 90 s) and, on contact, are spent and turn the body into a Flood combat form 2.5 s later, and Infection Forms leap at a target 2.5 to 7 Halo units away every 1.5 to 3 s. These extra forms are not part of any encounter, so `ai_living_count` ignores them.

## Factions and special enemies

**Teams and allegiances.** The engine has six teams (`halo_ai.h`): Covenant, human, Flood, Sentinel, player and "other" (the retail teams 6 to 9). An actor's team is its encounter's team, or on the default team its unit's default team from the biped tag (`actors.txt` `team`, read at unit +384: marines and crew human, Covenant and Engineers covenant, the Flood flood, Sentinels and the Monitor sentinel). Every team is hostile to every other except its own and the allegiances set; the player and the humans start allied (the missions also say so). `ai_allegiance` and `ai_allegiance_remove` set and clear an allegiance between two of the script's team literals, and the actors' targeting, hearing and shot hits follow the matrix at once, so Covenant, Flood and Sentinels now fight each other (c40, d20, d40) and c10 and c20's Sentinels fight beside the player. Allegiances reset when a mission starts, a checkpoint keeps them and a revert restores them, and saved games write them in the state block (`s allegiance <allied> <broken>`, optional on reading). Who counts as an ally (the motion tracker's yellow, enemies left in a wave, aim assist, `game_safe_to_save`, and the QA hooks that pick or clear hostiles: the route walker in `retail_qa.inc`, which also spares the passive Monitor and Engineers, `combat_qa.inc` and `damage_qa.inc`) asks the matrix. An actor whose target's team becomes an ally drops that target at once. A saved checkpoint writes the checkpoint's allegiances (not later betrayals); a mission or a section started afresh resets them even when it has no script. Infection Forms from a Carrier, and combat forms rising from bodies, are on the Flood team (they were Covenant).

**Betrayal.** When the player kills two members of a team allied with the player (the count is the engine's choice; Halo turns allies on a player who keeps killing them), the allegiance breaks: that team turns hostile, the console says `Halo: the human turn on the player`, and `ai_allegiance_broken` answers true for the pair (a50's `traitor_bitch`) until `ai_allegiance` renews it. Kills the scripts deal in the player's name (`ai_kill`, `ai_erase`, `ai_erase_all`, `damage_object`) do not count.

**Material damage.** `tools/halo_weapons.py` writes after every melee and projectile line of `weapons.txt` and after the grenades' blast and attached lines of `equipment.txt` a `materials` line: the `jpt!` tag's 33 damage modifiers, one per retail material type (`jpt!` +512). `tools/halo_actors.py` writes each variant's collision materials (`coll` +564, 72-byte entries: type, head flag, body and shield damage multipliers). For Hunters, Sentinels, the Monitor and Engineers `halodamage` multiplies the hit by the material's body multiplier times the weapon's modifier for that material; other bodies take damage as before (applying the material model to them too would change every time to kill and is left for a balance pass). Hits carry their `jpt!` (projectiles, blasts, grenades and the player's melee); a hit without one uses modifier 1 (0.5 on Hunter armour). `halo_damagetrace 1` logs `DAMAGE_MATERIAL` for these hits.

**Hunters.** From the tags: the shield arm (material hunter shield, body multiplier 0; every campaign weapon's modifier for it is 0 except the energy sword's) takes a direct hit from within 60 degrees of where the Hunter faces, so frontal fire does nothing; a hit from behind (beyond 130 degrees) lands on the exposed skin (hunter skin, multiplier 1, flagged as head: the pistol 1.0, assault rifle 0.5, shotgun 1.0); anything else, and every blast whatever the facing, lands on the armour plates (hunter armor: pistol and shotgun 0.2, assault rifle and plasma 0.5, frag and plasma grenades 0.25, rocket 1.0). The engine has no hit locations, so the region comes from the attacker's bearing; the belly, and headshot bonuses, are not modelled. Hunters pair off with the nearest unpartnered Hunter of their team (bond brothers) and rejoin a partner more than 10 units away; when one dies the other goes berserk for good and charges whoever killed it. Inside 1.6 world units a Hunter closes in and smashes: the unit's melee `jpt!` (35 to 45; `actors.txt` `unitmelee`) every 1.6 to 2.2 s with a shove, through the usual difficulty scaling. Further out it fires its fuel rod cannon from the tags (`hunter fuel rod`, its 75 to 40 blast), as before.

**Stealth Elites.** Variants with the `actv` active camouflage flag (the stealth Elites in a50, b30, b40 and c40, and d40's `floodcombat elite stealth unarmed`) are cloaked: actors see them only within about a fifth of their vision range (an eighth under super camouflage), as with the player's camouflage, and aim at them with extra error. They are drawn translucent through AssaultCube's translucent model path with a per-body opacity (`halomodelalpha`): a faint shimmer (about 0.05 to 0.13) that shows more of the body while the cloak flickers weaker, which it does for a second after the Elite fires or is hit (its cloak drops to about a third and recovers), the same fading the player's camouflage uses. Super camouflage (the stealth majors) hides a little more. A dead stealth Elite is visible. Spec-ops Elites have no camouflage flag in the Xbox tags and stay visible. Variants that cannot use ranged weapons (the energy sword Elites) now fight in melee with the sword's `jpt!` (151) times their damage modifier, at most one swing every 1.2 s.

**Flyers.** Actors whose `actr` has the flying flag (bit 21: Sentinels, the Monitor, Engineers) have no gravity, no jumping or landing and no ground snap (`halohovering` in `physics.cpp`; the player's movement is untouched); the brain sets their climb rate. They hold a height over the floor (a few times a second it traces the floor and ceiling under them: the retail BSP on retail collision, the cubes on stock geometry; over a drop with no floor in reach they hold the height they are at), fly straight to points instead of following the walking waypoints, and in combat hold 1.5 to 3.5 units over their target, keep their combat range and strafe across the target's line of fire, changing direction and height every 1 to 2.3 s. Killed, they fall. Sentinels fire their beam from the tags as before (a hitscan 1-point beam at 30 shots a second); the shielded variants have their `actv` shield (60). The brain's charge rule now reads the right `actr` flags (always charge; always charge or berserk while attacking): Sentinels and the Monitor no longer charge into melee, the Flood charges while attacking (all their squads start so), Infection and Carrier Forms always. **Enforcers** are a Halo 2 enemy: no Xbox Halo CE campaign cache has their tags, so there is nothing to place.

**343 Guilty Spark, Engineers, Keyes and Cortana.** The Monitor (`monitor` and `monitor_no_light`, kind 10) and the Engineer (kind 11) are new bodies: they fly, never fire or throw, and nobody targets the Monitor; its collision material has body multiplier 0, so it cannot be hurt (c20's scripts also set `object_cannot_take_damage`). c10, c20 and d40 have Monitor squads (c20 places them with `ai_place` and leads them with command lists), which it now follows in the air (`bsp0_monitor` to `bsp3_monitor` in c20). ## Retail mission scripting

The importer reads the original scenario syntax datum array, strings, script and global tables, oriented trigger volumes, camera points, flags, chapter strings, AI squads and conversations. It keeps the compiled nodes and their validated handles. The script import includes 1,673 device placements, 119 BSP switch records, and 349 recorded input streams across the ten missions. Some Xbox voice tags carry no subtitle text.

The client executes script expressions at 30 ticks per second. It handles script calls, startup and dormant threads, conditionals, timing, globals, original volume tests, supported hostile placements, conversations and checkpoint requests. It keeps thread and global state during the ordinary section-to-section handoff. Cinematic entry and exit cues connect the retail script functions to the current route. Those scenes use the original camera data, scripted audio starts and waits, and retail BSP and object assets. Camera transitions use the observer's quintic interpolation for position, field of view and axis-angle rotation, carrying velocity and acceleration across waypoints. Compressed skeletal clips are sampled at the retail cadence. The in-game console command `halo_scripttrace 1` logs camera cuts and audio starts. `halo_script_status` lists the unbound commands reached in the current mission. Save and pacing commands are bound: `game_safe_to_save` is false while a Covenant actor is in combat, `game_save_cancel` drops a pending checkpoint, and `game_revert` kills the player. One HUD countdown (`hud_set_timer_time`, `show_hud_timer`, `pause_hud_timer`, `hud_get_timer_ticks`) follows the engine's escape deadline on the Maw run, so d40's timer script no longer wakes `endgame_cinematics` early. Tutorial prompts (`player_action_test_*`) finish on the matching input or after five seconds, and presentation-only calls (rumble, rasterizer, screen effects, `display_scenario_help`, `enable_hud_help_flash`) are no-ops. Scenes the scripts call in the middle of a section, the scripts' moves of the player and the remaining unbound commands are under Script scenes and player moves. Nav points and the HUD show and blink commands are drawn (see Nav points and HUD script commands). `tests/test_script_coverage.py` fails if a command used in a `sleep_until` or `if` condition has no handler.

## Script scenes and player moves

**Not verified in the game yet**: written and compiled while testing was on hold. `tests/test_mission_exits.py` (new) and items 12 and 13 of `tests/test_frontend_progress.py`, item 3 of `tests/test_script_coverage.py` and the title check of `tests/test_campaign_ending.py` are written but have not been run.

**Scenes the scripts call.** The cue table (`cues` in `source/src/halo_script.cpp`) has a fifth trigger, Call: when a gameplay thread calls a scene script that has a Call row for the section, the scene plays there and then, on the scene stage like any other cue, and the calling thread waits for it and carries on after the call (as in Halo, where `(if (cinematic_skip_start) (cutscene_rescue)) (cinematic_skip_stop) (ini_post_rescue)` runs the scene, then what follows it). The scripted objects are kept aside while it plays and put back after, except those the scene created or destroyed (d20's captain scene destroys the implants). ## Robustness, sanitizers and CI

**Not yet run** (written while testing was on hold); the test plan is in `tests/README.md`.

**Sanitizer build.** `-DHALO_SANITIZE=ON` (with `-DHALO_BUILD_QA=ON`, which it requires) instruments the whole build tree with AddressSanitizer and UndefinedBehaviorSanitizer (`-fsanitize=address,undefined`, without the `function` and `vptr` checks: the stock engine calls console commands through generic function pointers), with frame pointers and debug info. `./scripts/build-macos.sh --asan` configures and builds it in `build/macos-asan` (RelWithDebInfo), so `build/macos` stays the shipping build; `HALO_BUILD_DIR` picks another directory. `package-macos.sh` refuses to package a `build/macos` configured with `HALO_SANITIZE=ON`. The QA client links Apple's sanitizer runtime from Xcode (`@rpath/libclang_rt.asan_osx_dynamic.dylib`). UBSan findings in the stock engine that are triaged and harmless go in `tests/data/ubsan.supp` (empty for now); findings in the `halo_*` files are to be fixed.

**Soak.** `tests/test_soak.py` runs `qa_soak` (`tests/native/soak_qa.inc`): one QA client process loads all 55 sections in campaign order (the Crash Site's standalone map as a30's first) as section selects, twice by default, letting each run for 1.5 s (4 s with `--asan`) once its opening scene is skipped, and logs the process's resident size, peak and physical footprint after each (`tests/native/qa_memory.cpp`, Mach `task_info`). Memory per section goes to `build/qa/soak-memory.csv`.

## Title menu and saved games

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold. `tests/test_frontend_progress.py` is written but has not been run.

The app and `./scripts/play-macos.sh` now start with `halo_title` instead of `halo_campaign`: a title screen (a plain backdrop over the stock level the engine boots into) with the **Halo** menu from `config/halo.cfg`:

- **Continue** resumes the saved game: its section, at its last checkpoint when one was reached in that section, with the loadout (both weapons with their rounds or battery, frag and plasma grenades and the selected type, health and shield) and difficulty it was saved with. The entry shows the mission, section, difficulty and whether a checkpoint is saved, and is greyed out when there is nothing to continue. With a version 3 save the game resumes exactly at the checkpoint: Continue starts the section, skips its opening scene, loads the saved checkpoint into the in-memory checkpoint and reverts to it as a death would, so the mission script carries on with its threads, globals, doors and lifts, scripted objects, squads, nav points and HUD state as they were, the vehicles stand where they stood (a player saved in a seat continues in it), the weapons and equipment on the ground and the stock items are as they were, the scripts' limits on the player (`unit_set_maximum_vitality`, `unit_impervious`) hold, a running overshield or active camouflage keeps its time left, and a later death reverts there too. A save at a section's start (no checkpoint yet) holds the script carried in from the section before, and Continue resumes it at the section's start. Without a usable state block (a version 2 file, a save at the start of a mission's first section, or a block that does not fit, below) the mission script starts afresh on the section as before: its opening scene is skipped when resuming at a checkpoint, the player is put back at the checkpoint (with the engine's route stage and marker), and that spot becomes the checkpoint a death reverts to. On The Maw's run the escape countdown resumes with the time left at the section's start. All of this is unverified in the game; `tests/test_frontend_progress.py` (items 3, 4 and 8 to 11) checks it.
- **New Game** asks for a difficulty and starts The Pillar of Autumn from the beginning (the Crash Site preview when a10 is not imported). Unlocked missions stay unlocked; the saved game is replaced once the section starts.
- **Mission select** lists the ten missions; those up to the furthest reached are playable (all of them once the campaign is beaten), the rest are greyed out as locked or not imported. Picking one asks for the difficulty. The in-game pause menu (**Halo Campaign**, Escape) uses the same list; the `halo_mission N` console command is not restricted.
- **Settings** and **Quit**. Escape with no menu open on the title screen brings the menu back.

The pause menu keeps Resume, Restart section, Mission select, Difficulty, Settings and Quit, and adds **Main menu**, which shows the title menu over the paused campaign (Escape returns to the game). Console commands behind the menus: `halo_title`, `halo_new_game <0-3>`, `halo_continue`, and the menu helpers `halo_can_continue`, `halo_continue_label`, `halo_unlocked`, `halo_mission_state <1-10>` (1 playable, 0 locked, 2 not imported), `halo_mission_title <1-10>`, `halo_difficulty_name` and `halo_progress_note`. `halo_campaign` (resume the furthest section from its start) is unchanged; tests and `play-macos.sh '-e...'` pass their own start command, which replaces `halo_title`.

The game is saved to `config/halo-progress.txt` in the profile at the start of every campaign section (section starts, section changes, restarts) and at every checkpoint, the engine's and the scripts' (`game_save`). Section selects and the Crash Site preview are not saved. The file is version 3, one record per line (`furthest`, `beaten`, `game`, `checkpoint`, `vitals`, `grenades`, `weapon` by retail tag path, `current`, `stock` for the fallback weapons without `weapons.txt`, then the state block) closed by a `check` line holding an FNV-1a hash of the rest. Version 2 files (the same without the state block) and version 1 files (`1 <mission> <section> [1]`) still load; a version 1 file's Continue starts the furthest section from its start.

The state block (`source/src/halo_state.h` for the record syntax) starts with `state <format> <mission> <section> <checkpoint> <.hscb hash> <section map hash> <records> <hash>`, the last two the number of records that follow and their own FNV-1a, so a damaged block is found even when the file's check holds. Its records are `s` (the mission script, `halo_script.cpp`): what the in-memory checkpoint keeps for a revert (every global by name, each thread by script name with its whole call stack, the scripted objects that differ from their defaults by object name, the living squad members by encounter, squad and start, every device group and device by object name, the external globals, the objective and help text, nav points, the HUD parts hidden or blinking, the chapter and the tick) and what the scripts set on the AI and a revert leaves alone (actor lists, `ai_link_activation`, migration targets, the platoon rules that fired, `ai_grenades`, the HUD timer); `v` (`halo_vehicle.cpp`): each vehicle of the checkpoint by vehicles.txt type and scenario object, its pose, motion, script settings, gun, safe spots and the player's seat (other riders and times in milliseconds are not kept); `w` (`halo.cpp`): the weapons and equipment on the ground (by tag path, scenario object and flags) and the stock items' spawned flags; `p`: `unit_set_maximum_vitality` and `unit_impervious` on the player and the powerups' time left. A save at a section's start writes only `s` and `p`, and only when the script was carried in (a section opened by the one before it, or continued); its opening scene ends first. Text is escaped so a record is one line; text and object pointers are written as offsets and indices; thread frames are the `.hscb`'s node datums. Continue checks the block before anything changes: its header, count and hash; that it is for the saved section; that the loaded `.hscb` has the hash it was saved with (frames mean nothing in another one); that every name matches the index it was saved at, every table has the size it had, and every frame's node exists. If any of that fails, the script restarts on the section as before, and the log (`Halo: The checkpoint's mission script state could not be restored; the script restarted on this section (<why>)`), the title menu's header and the pause menu's header warn about it; the Continue entry already says `(scripts changed: the section's script restarts)` when the `.hscb` on disk has another hash. If only the section map (`.cgz`) changed, the script's state is kept and the vehicles and ground items go back to their placements, with a warning. A file is expected to hold a few hundred kilobytes, perhaps a few megabytes late in a long mission (not measured; it is read up to 32 MB). Each save writes a temporary file, moves the previous file to `halo-progress.txt.bak` if it is valid, then renames the new one into place. On launch a progress file that fails its check is moved to `halo-progress.txt.corrupt` and the backup is restored and rewritten; the log (`campaign progress was corrupt ... restored from the backup`), the title screen and the title menu's header warn about it. With no usable backup progress is reset, with the same warnings. A save interrupted between its two renames is recovered from the temporary file.

Loadout persistence also applies within a session: finishing a section carries what the player carries into the next section of the same mission (Halo's sections are BSP switches), and a revert before the section's first checkpoint, or Restart section, returns to the loadout the player brought into the section rather than the default assault rifle and pistol. A new mission starts with the default loadout.

Limits: a save during a cutscene keeps no script state. Actors come back at their squad starts, as after a death revert (not where they stood). A revert after Continue at a checkpoint clears the overshield and camouflage, as any revert does; Continue at a section's start makes the carried script the state a death before the first checkpoint reverts to, as a live session now does too (Script scenes and player moves). Re-importing the scripts (`import_halo_scripts.py`) changes the `.hscb` hash, so saves made before it continue with the script restarted. The file keeps only the checkpoint's loadout, so Restart section after a Continue at a checkpoint starts the section with that loadout, not the one the player first brought into it. Under the title menu at launch the stock level the engine boots into keeps running.

## Nav points and HUD script commands

**Not verified in the game yet**: written and compiled while testing was on hold. `tests/test_nav_points.py` is written but has not been run.

The mission scripts' nav point commands are bound: `activate_team_nav_point_flag <type> <team> <flag> <offset>` and `activate_team_nav_point_object <type> <team> <object> <offset>`, the per-unit `activate_nav_point_flag` and `activate_nav_point_object`, and the four matching `deactivate_*` commands (single player: the team or unit is not checked). A point is a cutscene flag or an object (it follows the object), raised by the offset in Halo world units; activating the same flag or object again replaces it. Nav points are saved with each checkpoint and restored by a revert, carried across sections within a mission and cleared when the mission script starts afresh. `source/src/halo_hud.cpp` draws them with the retail waypoint arrows: `tools/halo_hud.py` now exports the HUD globals' `hud_waypoints` bitmap and its ten arrow types (name, colour, opacity, on-screen, off-screen and occluded sequences) as `waypoint` and `arrow` lines in `packages/halo/hud.txt` (re-run `python3 tools/halo_hud.py "$maps"`; the bitmap ids of the other sheets shift, and the exporter now compares page contents so the copied textures follow). A point on screen gets the type's on-screen marker in its colour (blue for `default`, red for `default_red`); a point off screen or behind the view gets the off-screen arrow on the screen's edge, turned towards it. Occlusion is not tested, so the occluded sequence is not used. Without those lines the points are drawn as diamonds and edge triangles. While any nav point is active, the engine's own route diamond is hidden.

`hud_show_health`, `hud_show_shield`, `hud_show_motion_sensor` and `hud_show_crosshair` hide and show those parts of the retail HUD (and of the fallback HUD), and `hud_blink_health`, `hud_blink_shield` and `hud_blink_motion_sensor` flash them, as a10's cryo tutorial does on Normal (it hides the health, shield, motion sensor and reticle and reveals each in its lesson). The state is saved with checkpoints and reset when the mission script starts afresh. `hud_set_objective_text`, `hud_set_help_text` and `show_hud_help_text` were already bound. `show_hud` (the chapter title scripts) and `display_scenario_help` stay no-ops.

The retail reticles now hang from their registration point measured from the sprite's own corner (as the exported sheets store it), not from the page's; reticles on combined sheets whose sprite is not in the page's top-left corner were drawn off centre before. Also unverified in the game.
