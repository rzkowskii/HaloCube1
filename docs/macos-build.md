# Build Halo in AssaultCube on macOS

The engine source comes from AssaultCube Lockdown Edition v1.3.0.2, commit `1ece5af7533983bb8f827616381d282470793d90`. Engine and ENet notices are in `source/`. Stock data is read from a local AssaultCube RC1 release. The ten Halo missions, viewmodels, characters, compiled mission scripts, cinematic geometry and audio are generated from expanded Halo CE Xbox map caches. [AssaultCube v1.3.0.2](https://github.com/assaultcube/AC/tree/v1.3.0.2)

## Dependencies

Install Apple's command line tools, Python 3.9 or later, CMake, and the Homebrew formulae `sdl2-compat`, `sdl2_image`, `libvorbis` and `libogg`. The cinematic audio importer uses FFmpeg. The client uses the system OpenGL and OpenAL frameworks. `CMAKE_PREFIX_PATH` can point CMake at libraries outside the default Homebrew prefix.

```bash
brew install cmake sdl2-compat sdl2_image libvorbis libogg ffmpeg
```

Set `AC_ASSET_ARCHIVE` to the original `AssaultCube_v1.3.0.2_LockdownEdition_RC1.tar.bz2` file. The scripts also look for it in `~/Downloads`. The staging script checks its SHA-256, extracts game data and retains the bundled license in `build/runtime/docs/license.html`.

## Import, build and play

Run from the repository root with the directory that contains the expanded North American Xbox Halo CE 1.0 maps. Halo3DS's prepared `halo-source` directory has this layout. The campaign import needs all ten mission caches; the asset library also imports any multiplayer and menu caches in the same directory.

```bash
maps="/path/to/halo-source"
./scripts/import-macos-assets.sh "$maps"
./scripts/package-macos.sh
```

Open `build/Halo in AssaultCube.app` in Finder; it opens on the title menu (see Title menu and saved games). The app includes the staged data and converted files from `packages/`. `package-macos.sh` copies the non-system dylibs (SDL2, SDL2_image, Vorbis, Ogg and their dependencies) into `Contents/Frameworks`, rewrites their install names to `@executable_path/../Frameworks`, ad-hoc signs everything and fails if any `/opt/homebrew` path remains, so the app can be moved to another Apple Silicon Mac. It always verifies the full 55-section import (all `.cgz/.cfg/.mesh`, the `.hcol` files of the retail-collision missions, driven sections included, the ten `.hscb` and the weapon, equipment, actor and vehicle tables) and exits non-zero if anything is missing; pass `--partial` for a development package that only needs the Crash Site files, and set `HALO_PACKAGES_DIR` to package another asset directory. It also runs `scripts/check-no-retail.sh`, which fails if a retail-derived file is tracked, staged or not ignored (everything under `packages/` is ignored except `maps/halo_a30.cfg`). Licences ship in `Resources/licenses`; see `NOTICE.md`. Run `./scripts/build-macos.sh` and `./scripts/play-macos.sh` for source development. The campaign importer supports `--mission` and `--part` for focused map edits. The script importer supports `--mission` and can regenerate the cinematic BSP meshes and models with `--rebuild`. Run `python3 tools/import_halo_scripts.py "$maps" --mission a10` before repackaging to upgrade an existing Autumn flyby mesh.

`build/retail-assets/catalog.json` indexes the local development library. It records every cache and tag, all BSPs, scenario placement tables, animation tracks, and looping sound definitions. The library copies the original caches into `sources/` and exports first-person and static models, full BSP meshes and collision, bitmap PNGs, and sound variants. Bitmap exports include cubemap faces and volume slices; P8 bump images preserve palette indices. WAV assets preserve the original Xbox sample encoding. The catalog records conversion gaps, and the copied caches retain the original data for future work. The campaign app uses its own converted media; multiplayer flow, the original menu, and additional weapon behavior still need engine integration. Rerun only the library with `python3 tools/import_halo_library.py "$maps"`; add `--rebuild` to regenerate converted assets.

The Silent Cartographer uses retail collision across all three sections. To update an existing campaign install, regenerate the maps and script projections, then package the app.

```bash
python3 tools/import_halo_campaign.py "$maps" --mission b30
python3 tools/import_halo_scripts.py "$maps" --mission b30
./scripts/package-macos.sh
```

The original structure collision surfaces handle movement, weapon traces, and bot sight. Follow the path from the beach to the facility, use the Cartographer terminal, and climb back to the surface. Press **E** near the Pelican's rear ramp once it reaches the landing zone. The adapted entry leaves the security door open so the route starts at the descent.
To launch that section directly, run `./scripts/play-macos.sh '-ehalo_section 4 2'`.

### Retail collision for other sections

The engine plays any section on the original structure collision when `packages/maps/<section>.hcol` exists and loads (`Halo: loaded N retail collision surfaces for <section> (M static machines)` in the log); a missing file means stock AssaultCube geometry, and a file that fails validation is reported (`retail collision unavailable`) and also falls back to stock geometry. `tools/import_halo_campaign.py --collision validated|all|none` chooses the sections that get one: `validated` (the default) covers the missions in `VALIDATED_COLLISION` (a10, a30, a50, b30, b40, c10, c20, c40, d20 and d40) except the sections in `STOCK_SECTIONS`, which keep stock geometry (and need no `.hcol` in `package-macos.sh`); `all` writes every section, `none` removes them. For those sections the importer also

- projects each section's BSP with that section's own projection (b30's return reuses section 1's, which is why `halo_b30_03.hcol` is identical to `halo_b30_01.hcol`),
- bakes the scenario machines that never move (bulkhead frames, consoles, a10's jammed bulkheads, which the mission script creates) into the `.hcol` as their real collision polygons, listed in a `DEV1` trailer so the engine stops colliding with their coarse boxes; machines a script switches to a `door_off` permutation (a50's cell doors) keep the engine's removable box; machines that move only in a cinematic (`CINEMATIC_STILL`: c20's `index_platform`) are baked in their first pose,
- treats a closed one-sided door (it opens only for a player behind it) walked into from the front as a door to wait at if a script makes it two-sided or opens it, and as a wall otherwise,
- plans the walkable route, spawns, markers and items on floors with room for the body (walls, shelves, railings and invisible stair ramps included), routes round open door panels, crouches through crawl spaces, jumps low obstacles and gaps, waits at a door only if a script opens it and there is no other way (doors that scripts only close, and those in `NEVER_OPEN`, are walls), walks through the objective volumes the script waits for, or up to a control it waits for the player to use (`SECTION_OBJECTIVES`, which the section's projection also covers), and starts a section past the door its entry script shuts behind the player,
- goes round the vehicles parked in the section when it starts (`VehicleBlocks` in `tools/import_halo_campaign.py`), as the engine's bodies collide with them: the box `source/src/halo_vehicle.cpp` gives the vehicle (the retail model's length, a width centred on its axis and its height above the floor, at the section's scale) at the placement's map cell and heading, widened by the body and the walker's drift, from 0.25 units below the retail point to its top (a body within 0.42 AssaultCube units of the top stands on it). Placements a script creates (not-placed flag 1: most of a50's turrets, d40's trench jeeps, b40's `crev_ent` turrets) are not there when the walk passes and are left out, as are those no difficulty places; turrets, Ghosts, Wraiths, Banshees and Warthogs all count. A jump may not pass through one, and actors, weapons and equipment are not put inside one. The importer lists each walked section's obstacles (`route avoids parked vehicles ...`),
- treats lift platforms (b40's `lift_a` to `lift_d`, c10's `lift_a`, `lift_b` and `lift_d`) as something to stand on but not walk through, and can route a lift ride: a `SECTION_OBJECTIVES` control followed by the retail point where the ride sets the player down,
- treats a closed door that a script destroys (c10's `post_helmet_door_3`, replaced by a bashed-in door after the x50 scene), or whose device group a script opens (c20's floor doors, `device_group_set floor1_door1 door_open`), as a door to wait at, not a wall,
- never jumps through a sealed door or an open door's panels (door panels are not in the BSP, so the jump test missed them); a jump over a scripted door stays free, as a10's cryo jump tutorial needs. The next a50 import changes `halo_a50_02.route`, which jumped through `gravity_door_lr`'s open panels; the other validated routes are unchanged,
- walks off a ledge onto a floor further down than a jump drops only in the sections listed in `LEDGE_DROPS` (d20 sections 2 and 3, up to 3 and 2.6 units), at the cost of a 300-step detour, so other routes are unchanged; a section whose exit volume hangs in a shaft past the last floor (`EXIT_FALLS`: d20 section 1) ends its route with one more step over the shaft,
- in the missions in `UNGROUPED_DOORS_SEALED` (d40), treats a closed unnamed door with neither a power nor a position group as a wall: no script names it and nothing drives it, and a manual or unpowered door does not open on approach. Elsewhere such doors still count as doors to wait at, as the routes were planned (and a10's walked); switching a mission over needs a re-walk,
- reports the scripted doors a route waits at (including those a jump passes over), an objective it cannot reach (`no route to <volume>`) and a route that ends outside its exit volume (`WARNING route ends outside its exit`),
- walks c10's light bridges as floor once extended (`LightBridges` in `tools/halo_collision.py`: flat machine panels that slide out over a pit; the extended pose is the end of the animation whose panels join into one strip). Stepping onto a bridge that starts retracted costs as much as a scripted door, and is allowed only if a script extends it (`flicker_bridge` moves `bridge_c`) or one of its controls is within reach of the step before; `bridge_a`, whose only control is on its far side, cannot be crossed from lift_a's side. Bridge decks are kept out of the native cube floor, so actors, items and weapons are not placed on them,
- for the sections in `LIFT_RIDES` (b40 section 6, c10 sections 1 and 4, c20 sections 1 to 3, d40 section 5) writes one more route row on the lift's deck: beside the lift's control when one of the lift's controls is within reach of the deck (the walker uses it there to send the lift), else at the deck's centre (the Library's platforms rise once the player stands on them, d40's elevator once enc5_3 holds every player), with the lift position at which the deck is at that landing. The row is in the route file only; spawns, markers and items stay on retail floor,
- writes the route (`x y z [flags [device@position]]`, flag 1 crouch, 2 jump, 4 the first step after a lift ride, 8 a walk off a ledge, 16 a lift's deck row, 32 call the lift from the landing (no script moves it) or use a bridge's control, 64 send the lift from the control on its deck, 128 a step on a light bridge that has to be extended) to `packages/maps/<section>.route` for `tests/test_retail_collision.py` (`tests/test_traversal_routes.py` checks the lift and bridge rows).

A scenario may give several trigger volumes one name (b40 has a `bsp 11,2` and a `bsp 2,11` at each of the c1 tower's two doorways). `SECTION_ANCHORS`, `TRANSITIONS` and `SECTION_EXITS` name the n-th of them `<name>#<n>`, in scenario order; a bare name is the last for anchors and the first for exit volumes. In the engine a BSP switch volume that holds the player when a section starts fires only once the player has left it, and is ignored for the whole section when another volume switches to the same BSP (the doorway the section was entered by).

Parked vehicles changed four routes, each of which walked through or brushed a parked vehicle before (checked statically against the planner's box, and against the engine's box at the map's placement with the body's 1.1-unit radius: the old routes had rows inside, the new ones none): `halo_b40_02.route` crossed `ext_a_bridge_turret_a` and `ext_a_bridge_turret_c` on the a2 tower's bridge (18 rows inside the planner's box, 16 inside the engine's; now 366 rows, was 334), `halo_b40_05.route` crossed `ext_c_banshee_a` and `ext_c_banshee_b` (27 and 26 rows; now 317, was 305), `halo_b40_07.route` brushed `zig_top_turret_a` (7 rows inside the planner's margin, none inside the engine's box; 817 rows as before, 20 of them moved) and `halo_c40_03.route` crossed the unnamed Ghost at (157, -336) in the canyon (6 and 5 rows; 1606 rows as before, 90 moved). Every route still ends where it did. Their section maps changed with them (spawns, markers and the stand-in items follow the route; the cube geometry is unchanged), and `halo_a50_01.cgz` moved one actor spawn out of a turret's box; every other route and section map is byte for byte as it was. None of these has been walked. Re-run `import_halo_campaign.py "$maps" --mission b40` and `--mission c40` (after `tools/halo_vehicles.py`, which writes the boxes' sizes; without `vehicles.txt` the planner ignores vehicles) to regenerate them.

Movement on retail collision uses the stock physics unchanged (ground speed 16, acceleration, friction, jump). The collision layer slides along walls, corners, door panels and other bodies, and climbs device and mapmodel tops below the step height, so nothing the stock geometry slid along snags; allies the player walks into step aside. The test measures this against the stock geometry of each section.

### Falls, wedges, lifts and light bridges

None of this has been verified in the game yet: it was written while testing was on hold. `tests/test_retail_recovery.py`, `tests/test_traversal_routes.py` and the lift and bridge walks of `tests/test_retail_collision.py` (`PENDING_WALK`) check it once testing resumes.

- Falls out of the world. On retail collision a body can fall through a hole or seam in the structure, which the stock cube grid never had. The engine (`updateRecovery` in `source/src/halo.cpp`) keeps the last eight retail floor spots the player stood on, at least 2 units apart (only real structure floor counts: not a lift deck or a light bridge, which move or vanish). A player whose feet are more than 8 units below the section's mesh, or who has been in the air for two seconds with neither structure nor device below down to that depth, is put back on the newest of those spots that is still clear (`Halo recovery: fell below the retail collision, player put back at x,y,z`, or `fell out of the world`). A second recovery within five seconds goes one spot further back. If none is clear, the player dies and reverts to the checkpoint as usual. Actors (enemies and allies) whose feet fall below that depth die, as in Halo. Ordinary falls, into a pit with a floor, or d20's jump into the shaft its exit volume hangs in, never reach that depth or that airtime over nothing, and the checks do nothing on stock geometry, during cinematics or once a section is complete.
- Wedges. A player whose body overlaps the structure by more than 0.1 units or is inside a device's box (a door or a lift deck closing on them) for 0.75 s, or who has been in the air without moving at all for 1.5 s (caught in a crease too steep to stand on), is moved to the nearest clear retail floor within 3 units (`wedged in the collision`, `stuck in mid-air`), or failing that to a safe spot as above. A player wedged before standing on any retail floor since the last move that was not walking (a spawn, a revert to a checkpoint on a lift deck, a teleport) is not reverted, which would put them back in the same place and loop: they are left where they are (`no safe floor since the checkpoint, player left in place`) and checked again five seconds later. A spot inside a vehicle's footprint (one parked there since) is neither recorded nor used. None of these checks run while the player is in a vehicle seat; the vehicle has its own stuck recovery (see Vehicles). A player thrown out of a vehicle onto it, with no room for the body beside it, whom these checks find wedged or falling within 15 s, without having taken a seat since, is put back in that seat instead (not after the vehicle itself fell out of the world), the vehicle righted where it lies or moved to where it fits (`Halo recovery`'s reason, then `player put back in the Warthog at x,y,z`): in the Maw's run the driver has never stood on retail floor, and this used to log `player left in place` every five seconds. Moves that are not walking reset this recovery (see the next item).
- Moves that are not walking. Every move of the player other than walking goes through one helper, `haloplayermoved` in `source/src/halo.cpp`: a spawn or revert, Continue, a section start (BSP switches end a section, so this covers them), the end of a cutscene (the Cartographer's handoff moves the player; every scene's end is treated the same), getting into a vehicle seat (the scripts' `vehicle_load_magic` and `unit_enter_vehicle`, a revert or the Maw's escape seating the player, a reclaim) and out of one (beside it, or thrown onto it), and every QA hook that teleports the player (`tests/native/*.inc`, except `qa_retail_recover`, which stands in for a fall or a wedge). It drops the safe spots recorded before the move, so the recovery never puts the player back on a floor from before a teleport, restarts the wedge and stall timers, and starts a one-second grace in which the wedge and stall checks do not count (the falls are still checked): a wedge right after a move is nudged after 1.75 s instead of 0.75 s. Getting into a seat keeps one safe spot, the retail floor the player got in from: when the vehicle falls out of the world with no safe spot of its own, the driver goes there (`halorecoverplayer`) rather than dying. With `halo_scripttrace 1` each move is logged (`Halo moved: <why>, N safe floors dropped`). The mission scripts' player teleports (`object_teleport` of the player, as in d20's captain scene and d40's bridge) are still not performed, so they do not move the player. Not verified in the game: `tests/test_retail_recovery.py` checks it (`qa_halo_moved`).
- Lifts. Everyone standing on a lift's deck is carried with it: the player, allies and enemies, on retail collision as on stock geometry. On a rising deck a body counts once any part of it is over the deck, as the device collision stands it there, so the deck no longer lifts into someone on its edge and wedges them (only the player whose centre was over the deck used to be carried). A descending deck carries only the bodies whose centre is over it, so someone standing on the landing beside a flush deck is not dragged down through the landing's floor. A lift's deck at rest may stand higher above its landing than a step: the Library's platforms are 0.38 units up at the bottom of their shafts, 2.6 units at floor 1's scale, against a 1.26-unit step. A grounded body may step onto a lift deck from up to 0.45 retail units below its top (`Scenario::liftBoard`); nothing else changes the step height. The device's collision is its boxes in the current animation pose, so it moves with the lift.
- Light bridges. A light bridge is a machine whose panels slide out over a pit; the engine collides with each panel's box in its current pose, so an extended bridge is floor and a retracted one leaves the pit open. A bridge that retracts under the player (c10's flickering `bridge_c`) drops them into the pit; if the pit has no floor, the fall recovery puts them back on the last floor they stood on. The route planner models them as above (`LightBridges`).
- The QA walker (`tests/native/retail_qa.inc`) boards, calls and sends lifts at deck rows, waits two rows short of a light bridge until it is extended, and after a recovery carries on from the nearest route row behind it. See `tests/README.md`.
- Stock sections. With this, c10 section 2 moved to retail collision (below). c10 sections 3, 5 and 6 were re-planned with the bridges and lifts modelled and still have no way through (below); c40 sections 1 and 4 need lifts in BSPs that are not campaign sections (or a Banshee), and d40 section 3 has no walkable link between its floors, so they all stay stock, and a30's first section is the standalone map. d40 sections 6 to 8, the Warthog run, are `DRIVEN_SECTIONS`: they get an `.hcol` for the Warthog and no walking route (see Vehicles).

## Vehicles

**Not verified in the game yet**: everything in this section was written and compiled while testing was on hold, the vehicle fixes (bodies inside vehicles, shoving, stuck recovery, the escape taking over a scenario Warthog, lift decks, routes round parked vehicles) included. `tests/test_vehicles.py` (items 7 to 9 for the fixes), `tests/test_maw_drive.py` (item 6) and the parked-vehicle check in `tests/test_traversal_routes.py` are written but have not been run.

`tools/halo_vehicles.py "$maps"` (run by `import-macos-assets.sh` before the campaign import) writes `packages/halo/vehicles.txt` from the retail `vehi` tags and exports their models to `packages/models/halo/vehicle/<name>` (git-ignored, like everything under `packages/`). It lists six vehicles in a fixed order: the Warthog (a car the player drives), the Covenant gun turret (a fixed gun with a gunner seat), and the Ghost, Scorpion, Banshee and Wraith (parked props: nobody drives or flies them yet). Each record carries the drive parameters, the model's bounds, the seats with their markers and the vehicle weapon from `weapons.txt`. `package-macos.sh` requires the file. Without it the engine falls back to a built-in Warthog with the model the actor importer writes to `packages/models/halo/warthog`; a vehicle with no model is drawn as a wire box.

`tools/import_halo_campaign.py` writes each mission's scenario vehicle placements (the `scnr` vehicle block) of those six types into the sections whose BSP holds them, as `PLAYERSTART` entities with team 102: the type, the placement's not-placed flags, the scenario object index and the section scale. On retail collision they stand at their retail point and settle onto the floor; on stock geometry they go on the nearest raster floor. Placements the scripts create (`object_create`, not-placed flag 1) appear when the script creates them; the others appear at the start, except on the difficulties their flags leave them out of. Re-run the campaign import (all missions) to place them. Imported: d40's six parked escape Warthogs in section 6, a Warthog and a turret in section 7 and the two enc7_7 turrets in section 8; a50's 14 turrets; the Warthogs, Ghosts and Banshees of a30, b30 and c40; b40's turrets, Ghosts, Wraiths and Banshees (its Scorpion stands outside every campaign section); the turrets of c10 and d20. Pelicans, dropships, lifepods and cinematic props are left out.

`source/src/halo_vehicle.cpp` runs them:
- **E** by a seat's door gets in (the driver's door of a Warthog, its rear for the gunner's seat, a turret's gun); in a seat **E** gets out beside the door, or on the other side, behind, ahead or on top, wherever the body fits, and stays in when none does. A seat nearer than a weapon on the ground wins **E**. The HUD prompts `E  Drive the Warthog`, `E  Warthog gunner`, `E  Man the Covenant Turret` or `E  Flip the Warthog`.
- The Warthog drives with **W**/**S** (throttle, brake, reverse) and steers towards where the camera looks, as the retail Warthog does; **A**/**D** steer directly. `halo_vehiclesteer 1` steers with the keys only. The camera orbits behind with the mouse. Top speed is the retail Warthog's at the section's scale, and never below 36 units/s (the old escape pace, which the 3:00 timer was set for); grip is strong with some slide, it climbs and jumps off crests, pitches and rolls with the ground, and flips when it lands on its side or back or stands over more than 58 degrees. Upside down for 0.7 s it throws the driver out; **E** beside a flipped vehicle puts it back on its wheels. Running into actors at speed kills them. It is not the retail physics.
- The bodies are the retail vehicles' size at the section's scale. On retail collision the Warthog drives on four wheel traces and two chassis capsules against the structure and the machines (doors); on stock geometry on the cube grid (it steps up whole cubes as the walking body does). Bodies collide with vehicles (`halo_vehiclecollide 0` turns that off, for checking a route walk a placed vehicle blocks); the walking routes go round the parked ones (above).
- Bodies inside vehicles. A body (the player on foot or an actor not in a seat) left part way inside a vehicle's box, by a vehicle the script creates, spawns, teleports or a revert puts back over it, an exit spot or a lift, is pushed out within a frame by the shortest way that has room, checked against the retail collision (or the cube grid), the devices, the other bodies and the vehicles: out of each face at the box's edge, its corners, each face a body's width further out, nearest first, or onto the roof when the feet are within a step of it; first onto floor, then over a ledge, never through a wall or a closed door between the body and the spot (a line of sight at the body's middle) (`Halo vehicle: player pushed out of the Warthog (N units)`, actors with `halo_vehicletrace 1`). A body with no room anywhere may walk out of that vehicle and is tried again every quarter second (`... has no room to get out; it may walk out`). The old rule, by which only a body deep inside a box could walk out and one part way in could not move, is gone. Ordinary movement is unchanged: walking never enters a vehicle's box.
- A moving vehicle (the player's Warthog, or an empty one rolling) shoves each body it runs into out ahead of it or aside, a few hundredths of a unit clear, every 8 ms step; a body pinned against a wall (or another body or vehicle) stops it instead. The player's Warthog at more than 8 units/s still runs actors down as before, once a frame each (killed outright above 20).
- The Warthog's gunner seat and the turrets fire their retail gun (warthog gun, turret gun) at the crosshair with its rate and heat; the driver cannot fire. The HUD shows the vehicle, the seat, the speed or the gun's heat, and the shield, health and motion sensor. Fire on a player at the wheel of a Warthog is cut by a fifth; vehicles themselves cannot be destroyed (they cannot in Halo CE either).
- Stuck recovery (`updateStuck`), as for the player on foot. Each Warthog keeps its last four safe spots, sampled every quarter second: grounded, upright within 30 degrees, clear of the structure, the machines and the other vehicles, with all four wheels on structure floor (not a lift deck or a light bridge), at least half a length apart. One that falls out of the world (8 units below the section's mesh, below -130 on stock geometry, or two seconds in the air with neither structure nor device below), stays wedged (the chassis more than 0.1 units into the structure while slower than 2 units/s, for 0.75 s; the capsules' bottoms ride up with its pitch and roll, so a steep ramp is not a wedge) or hangs in mid-air without moving for 1.5 s goes to the nearest spot within two widths where it fits upright with floor under its wheels (not after a fall), else to its newest safe spot that is still clear, with whoever is in it (`Halo vehicle recovery: <why>, the Warthog put back at x,y,z`); a second recovery within five seconds goes one spot further back. With nowhere to put it, the driver is put out (`no safe spot for the Warthog, driver put out`): beside it after a wedge, and after a fall onto the retail floor the player got in from (`halorecoverplayer`; getting into a seat drops the other safe floors), else killed and reverted as before; an empty one that fell goes back to its placement (or is removed). Turrets and parked props never move by themselves and get only the fall check, so they stay where the scenario put them. Upside down beyond the flip helper: E on an overturned vehicle that would not fit upright where it lies moves it to the nearest spot where it does or to its last safe spot; a driver who has no room to get out of an overturned Warthog (0.7 s on its back) stays at the wheel and the Warthog is put back on its wheels, and only when that fails is the driver thrown onto it (and later put back in by the recovery, see Falls, wedges, lifts and light bridges).
- Lift decks: a vehicle standing on a device (not all four wheels on structure floor) never goes to sleep, so it keeps following its floor, and lifts carry vehicles up and down as they carry bodies. Only on retail collision: on stock geometry a vehicle's floor is the cube grid.
- The mission scripts' seat commands act on these vehicles: `vehicle_test_seat_list`, `vehicle_test_seat`, `unit_enter_vehicle`, `vehicle_load_magic`, `unit_exit_vehicle`, `vehicle_unload`, `vehicle_riders` (the player only), `vehicle_driver`, `vehicle_gunner`, `unit_in_vehicle`, `unit_set_enterable_by_player`, `object_create`/`_destroy` (a bulk destroy leaves the player's own vehicle alone), `object_teleport`, and `ai_vehicle_enterable_distance`, `_actor_type` and `_disable`, `ai_go_to_vehicle` and `ai_exit_vehicle` for turret gunners. A vehicle carried by a scripted object (b30's jeep under its Pelican) follows it until the script lets it go. A Warthog or turret that is not in the current section reports nobody in its seats; other vehicles keep the stand-ins (seat tests true). The Maw's escape seats the player in a scenario Warthog where one is parked (below); in the seat tests (`halovehicleescapeseat`) that Warthog is itself and stands in for the scenario Warthogs not standing in the section (in sections 7 and 8, `trench_jeep1` to `3` and `asspain_1` to `3`), and a Warthog the engine spawned (bound to no scenario object) stands in for every scenario Warthog, as before, so `trench_jeep_test` (which asks for `trench_jeep1` to `4` and `asspain_1` to `3`) sees the player at the wheel and Cortana does not nag. ## Retail weapons

`tools/halo_weapons.py` reads every `weap` tag in the ten campaign caches, follows each trigger to its projectile and damage tags, and writes `packages/halo/weapons.txt`. The game loads that table at startup. Rounds, reload time, rate of fire and its ramp, spread, heat, battery, charge time, zoom levels, aim assist, projectile speed and homing, and damage all come from the tags. The importer also records the first-person and pickup models from the asset library, so run it after `import_halo_library.py` and before `import_halo_campaign.py`. The campaign importer stores each enemy's carried weapon (from its actor variant) and the scenario's weapon placements in the section maps.

```bash
python3 tools/halo_weapons.py "$maps"
python3 tools/import_halo_campaign.py "$maps"
```

The player carries two of the nine campaign weapons. Walking over a weapon you carry takes its rounds, and **E** swaps the current weapon for one on the ground. **Mouse 2** or **Z** steps through the weapon's zoom levels. Holding fire charges the plasma pistol. Covenant weapons show battery and heat instead of rounds, and overheat. Enemies fire their actor's weapon with a reduced share of its damage and drop it when killed. Reticle artwork for weapons without a HUD tag, zoom sounds and the rocket launcher's first-person placement still need work.

**Damage (`jpt!`).** Weapons, melee and grenades read their damage with one layout, `JPT_*` in `tools/halo_weapons.py`, checked against the bytes of every campaign `jpt!` tag (not yet tried in the game). From the tag body: radius bounds at 0, cutoff scale at 8, flags at 12; the damage section at 452 holds side effect and category (two 16-bit enums), damage flags, the area core radius, then the damage lower bound at +12, the upper bound's min and max at +16 and +20, the vehicle passthrough penalty at +24, active camouflage damage, stun, maximum stun and stun time, and instantaneous acceleration at +48. The frag explosion reads 80 lower, 120-120 upper; the sniper bullet 101-101 with a 0.5 passthrough. The weapon reader used to take +16 (the upper min) as the lower bound and +24 (the passthrough) as the upper, so every weapon came out with lower equal to upper at the upper min; the grenade reader was right. `weapons.txt` and `equipment.txt` are now format 2: `projectile`, `melee`, `blast` and `attached` lines carry lower, upper min and upper max, and the game refuses a format 1 table, so re-run `tools/halo_weapons.py` after pulling this. A full-strength hit deals a random amount in the upper bound's range; the lower bound, what Halo scales a weakened hit down to (range falloff, the edge of a blast, a short fall), is carried but not applied: area damage still falls to none at the outer radius and there is no range falloff. The player's shots roll the range: the shotgun pellet 18-25 (was 18), plasma rifle 12-14 (12), plasma pistol 16-20 (16), rocket 300-330 (300); the assault rifle (10), pistol (25), sniper (101), needle (10), flame (10) and charged plasma bolt (70) are flat as before. The guns of vehicles the player drives or mans fire through the same code and roll too: the Warthog chaingun 16-24 (was 16), the Ghost and Banshee bolts 10-14 (10), the Scorpion shell 351. Melee rolls 50-60 (was 50; the flamethrower 70-80). Grenades roll 120-120 inside the inner radius where they rolled 80-120 before, and a stuck plasma grenade adds its attached 120 (240 in all), enough for an Elite Minor or Major on Easy and Normal; Heroic and Legendary toughen the Covenant by 1.25 and 1.5, so there it may not kill (not checked). Enemies, allies and the slot's nominal damage keep the upper min, the value their balance was set with, times the actor variant's damage modifier and the difficulty scaling, so enemy gunfire is unchanged (rolling the range for them would turn the Elite plasma rifle's 6 per bolt into 7 after rounding). Enemy grenades are not: every grenade's blast goes through the same roll, whoever threw it, so an actor's frag or plasma grenade inside its inner radius now deals 120 before the difficulty scaling where it dealt 80 to 120. Against the player's 150 of shield and health that is 120 on Normal (it was 80 to 120), 156 on Heroic (104 to 156) and 204 on Legendary (136 to 204): on Heroic and Legendary a grenade at the player's feet now always kills from full shield and health, the overshield's layers aside. A plasma grenade an actor sticks to the player adds its attached 120 and kills on every difficulty but Easy. None of this is checked against Halo or in the game; grenades were themselves new and untested before the layout change, so there is no tested balance to compare with.

## Actor AI

`tools/halo_actors.py` writes `packages/halo/actors.txt` from the campaign `actr` and `actv` tags: vision and hearing, firing range, rate and error, burst timing, combat range, target leading, grenades, vitality, shield-based hiding, panic chances, berserk thresholds and position hold times. Run it after `halo_weapons.py`. `import_halo_scripts.py` then writes version 6 `.hscb` files. These add each encounter's combat positions, squad states and position-group masks, platoon rules, per-start variants and command lists, and the scenario's command lists.

The campaign ending is driven by the scripts. `game_won` on The Maw's last section, or the finale cue finishing that section, starts an ending: a credits roll over the level (Enter skips), `config/halo-progress.txt` marks the campaign beaten (`beaten 1`, with every mission unlocked and no game left to continue), and the game opens the **Halo Campaign** pause menu over the level (its **Main menu** entry leads to the title menu). `game_won` on earlier sections is ignored, because sections advance on their own. `game_lost` kills the player so the normal revert applies.

Campaign bots think with `source/src/halo_ai.cpp` instead of AssaultCube's bot AI. AssaultCube still handles movement, pathfinding and physics. Actors:
- notice targets inside their vision cone, or hear gunfire, after a reaction delay
- alert nearby squadmates
- take combat positions from their squad's groups for attacking, defending or pursuing
- fire in retail bursts and throw grenades
- hide when their shields are low, panic when friends or leaders die, and go berserk when badly hurt
- follow command lists.

Marine and crew encounters now spawn on the player's side and fight the Covenant and Flood. Platoon rules switch squads between attacking and defending as casualties mount. The scripts' AI commands work, including `ai_actors` lists, `ai_status`, `ai_living_fraction`, `ai_strength`, magic sight, follow and fight orders, `ai_migrate` to new positions, command lists and their status, and `objects_can_see_*`. Vehicle seat and boarding commands act on the engine's Warthogs and turrets (see Vehicles); for other vehicles they are stand-ins. The AI, unit and object-state commands live in `source/src/halo_script_ai.inc`. `ai_berserk`, `ai_grenades`, `ai_allow_dormant`, `ai_maneuver_enable`, `ai_renew`, `ai_prefer_target`, `ai_follow_target_ai`/`_disable`, `ai_follow_distance`, `ai_braindead_by_unit`, `ai_free`, `ai_try_to_fight_nothing`, `ai_link_activation` (waking the linked encounter once one is alert), `ai_teleport_to_starting_location*`, and the migrations (`ai_migrate_by_unit`, `ai_migrate_and_speak`, `ai_attach` on an actor) change what the actors do; flags survive a revert. `object_cannot_take_damage`, `unit_impervious` and `unit_doesnt_drop_items` apply to actors and the player, `unit_set_current/maximum_vitality` set the player's health and shield (maximum shield 0 removes the shield) or an actor's fraction of spawn health, `unit_suspended` stops an actor thinking, and `object_set_permutation door_off` removes a cell door and its collision. `damage_object` and `damage_new` do not read the retail `jpt!` effects: names with guaranteed, doom, plummet or death kill, any other effect does 40 damage. Recorded but without visible effect: `unit_open/close`, `vehicle_hover`, `object_set_collideable`, `unit_set_enterable_by_player`, `ai_attach` and `ai_attach_free` on scripted objects, `ai_automatic_migration_target`, `ai_exit_vehicle` and `ai_vehicle_enterable_*` on vehicles the engine does not drive, `ai_allow_dormant` (no dormancy exists), `unit_set_emotion`, flashlight state and `ai_dialogue_triggers`. `(player0)` now evaluates to the player and `(player1)` to nothing. Balance has only been checked in short QA runs: enemies are accurate at close range.

Only living actors count towards the 128-actor cap on scripted placements; dead squad entries stay for `ai_living_fraction` and to stop a killed start respawning. The Flood life cycle is not scripted: a dying Carrier Form bursts into 4 to 8 Infection Forms, Infection Forms walk to a fallen marine or Elite (bodies last 90 s) and, on contact, are spent and turn the body into a Flood combat form 2.5 s later, and Infection Forms leap at a target 2.5 to 7 Halo units away every 1.5 to 3 s. These extra forms are not part of any encounter, so `ai_living_count` ignores them.

## Retail mission scripting

The importer reads the original scenario syntax datum array, strings, script and global tables, oriented trigger volumes, camera points, flags, chapter strings, AI squads and conversations. It keeps the compiled nodes and their validated handles. The script import includes 1,673 device placements, 119 BSP switch records, and 349 recorded input streams across the ten missions. Some Xbox voice tags carry no subtitle text.

The client executes script expressions at 30 ticks per second. It handles script calls, startup and dormant threads, conditionals, timing, globals, original volume tests, supported hostile placements, conversations and checkpoint requests. It keeps thread and global state during the ordinary section-to-section handoff. Cinematic entry and exit cues connect the retail script functions to the current route. Those scenes use the original camera data, scripted audio starts and waits, and retail BSP and object assets. Camera transitions use the observer's quintic interpolation for position, field of view and axis-angle rotation, carrying velocity and acceleration across waypoints. Compressed skeletal clips are sampled at the retail cadence. The in-game console command `halo_scripttrace 1` logs camera cuts and audio starts. `halo_script_status` lists the unbound commands reached in the current mission. Save and pacing commands are bound: `game_safe_to_save` is false while a Covenant actor is in combat, `game_save_cancel` drops a pending checkpoint, and `game_revert` kills the player. One HUD countdown (`hud_set_timer_time`, `show_hud_timer`, `pause_hud_timer`, `hud_get_timer_ticks`) follows the engine's escape deadline on the Maw run, so d40's timer script no longer wakes `endgame_cinematics` early. Tutorial prompts (`player_action_test_*`) finish on the matching input or after five seconds, and presentation-only calls (rumble, rasterizer, screen effects, `display_scenario_help`, `enable_hud_help_flash`) are no-ops. Nav points and the HUD show and blink commands are drawn (see Nav points and HUD script commands). `tests/test_script_coverage.py` fails if a command used in a `sleep_until` or `if` condition has no handler.

## Title menu and saved games

The app and `./scripts/play-macos.sh` now start with `halo_title` instead of `halo_campaign`: a title screen (a plain backdrop over the stock level the engine boots into) with the **Halo** menu from `config/halo.cfg`:

- **Continue** resumes the saved game: its section, at its last checkpoint when one was reached in that section, with the loadout (both weapons with their rounds or battery, frag and plasma grenades and the selected type, health and shield) and difficulty it was saved with. The entry shows the mission, section, difficulty and whether a checkpoint is saved, and is greyed out when there is nothing to continue. With a version 3 save the game resumes exactly at the checkpoint: Continue starts the section, skips its opening scene, loads the saved checkpoint into the in-memory checkpoint and reverts to it as a death would, so the mission script carries on with its threads, globals, doors and lifts, scripted objects, squads, nav points and HUD state as they were, the vehicles stand where they stood (a player saved in a seat continues in it), the weapons and equipment on the ground and the stock items are as they were, the scripts' limits on the player (`unit_set_maximum_vitality`, `unit_impervious`) hold, a running overshield or active camouflage keeps its time left, and a later death reverts there too. A save at a section's start (no checkpoint yet) holds the script carried in from the section before, and Continue resumes it at the section's start. Without a usable state block (a version 2 file, a save at the start of a mission's first section, or a block that does not fit, below) the mission script starts afresh on the section as before: its opening scene is skipped when resuming at a checkpoint, the player is put back at the checkpoint (with the engine's route stage and marker), and that spot becomes the checkpoint a death reverts to. On The Maw's run the escape countdown resumes with the time left at the section's start. All of this is unverified in the game; `tests/test_frontend_progress.py` (items 3, 4 and 8 to 11) checks it.
- **New Game** asks for a difficulty and starts The Pillar of Autumn from the beginning (the Crash Site preview when a10 is not imported). Unlocked missions stay unlocked; the saved game is replaced once the section starts.
- **Mission select** lists the ten missions; those up to the furthest reached are playable (all of them once the campaign is beaten), the rest are greyed out as locked or not imported. Picking one asks for the difficulty. The in-game pause menu (**Halo Campaign**, Escape) uses the same list; the `halo_mission N` console command is not restricted.
- **Settings** and **Quit**. Escape with no menu open on the title screen brings the menu back.

The pause menu keeps Resume, Restart section, Mission select, Difficulty, Settings and Quit, and adds **Main menu**, which shows the title menu over the paused campaign (Escape returns to the game). Console commands behind the menus: `halo_title`, `halo_new_game <0-3>`, `halo_continue`, and the menu helpers `halo_can_continue`, `halo_continue_label`, `halo_unlocked`, `halo_mission_state <1-10>` (1 playable, 0 locked, 2 not imported), `halo_mission_title <1-10>`, `halo_difficulty_name` and `halo_progress_note`. `halo_campaign` (resume the furthest section from its start) is unchanged; tests and `play-macos.sh '-e...'` pass their own start command, which replaces `halo_title`.

The game is saved to `config/halo-progress.txt` in the profile at the start of every campaign section (section starts, section changes, restarts) and at every checkpoint, the engine's and the scripts' (`game_save`). Section selects and the Crash Site preview are not saved. The file is version 3, one record per line (`furthest`, `beaten`, `game`, `checkpoint`, `vitals`, `grenades`, `weapon` by retail tag path, `current`, `stock` for the fallback weapons without `weapons.txt`, then the state block) closed by a `check` line holding an FNV-1a hash of the rest. Version 2 files (the same without the state block) and version 1 files (`1 <mission> <section> [1]`) still load; a version 1 file's Continue starts the furthest section from its start.

The state block (`source/src/halo_state.h` for the record syntax) starts with `state <format> <mission> <section> <checkpoint> <.hscb hash> <section map hash> <records> <hash>`, the last two the number of records that follow and their own FNV-1a, so a damaged block is found even when the file's check holds. Its records are `s` (the mission script, `halo_script.cpp`): what the in-memory checkpoint keeps for a revert (every global by name, each thread by script name with its whole call stack, the scripted objects that differ from their defaults by object name, the living squad members by encounter, squad and start, every device group and device by object name, the external globals, the objective and help text, nav points, the HUD parts hidden or blinking, the chapter and the tick) and what the scripts set on the AI and a revert leaves alone (actor lists, `ai_link_activation`, migration targets, the platoon rules that fired, `ai_grenades`, the HUD timer); `v` (`halo_vehicle.cpp`): each vehicle of the checkpoint by vehicles.txt type and scenario object, its pose, motion, script settings, gun, safe spots and the player's seat (other riders and times in milliseconds are not kept); `w` (`halo.cpp`): the weapons and equipment on the ground (by tag path, scenario object and flags) and the stock items' spawned flags; `p`: `unit_set_maximum_vitality` and `unit_impervious` on the player and the powerups' time left. A save at a section's start writes only `s` and `p`, and only when the script was carried in (a section opened by the one before it, or continued); its opening scene ends first. Text is escaped so a record is one line; text and object pointers are written as offsets and indices; thread frames are the `.hscb`'s node datums. Continue checks the block before anything changes: its header, count and hash; that it is for the saved section; that the loaded `.hscb` has the hash it was saved with (frames mean nothing in another one); that every name matches the index it was saved at, every table has the size it had, and every frame's node exists. If any of that fails, the script restarts on the section as before, and the log (`Halo: The checkpoint's mission script state could not be restored; the script restarted on this section (<why>)`), the title menu's header and the pause menu's header warn about it; the Continue entry already says `(scripts changed: the section's script restarts)` when the `.hscb` on disk has another hash. If only the section map (`.cgz`) changed, the script's state is kept and the vehicles and ground items go back to their placements, with a warning. A file is expected to hold a few hundred kilobytes, perhaps a few megabytes late in a long mission (not measured; it is read up to 32 MB). Each save writes a temporary file, moves the previous file to `halo-progress.txt.bak` if it is valid, then renames the new one into place. On launch a progress file that fails its check is moved to `halo-progress.txt.corrupt` and the backup is restored and rewritten; the log (`campaign progress was corrupt ... restored from the backup`), the title screen and the title menu's header warn about it. With no usable backup progress is reset, with the same warnings. A save interrupted between its two renames is recovered from the temporary file.

Loadout persistence also applies within a session: finishing a section carries what the player carries into the next section of the same mission (Halo's sections are BSP switches), and a revert before the section's first checkpoint, or Restart section, returns to the loadout the player brought into the section rather than the default assault rifle and pistol. A new mission starts with the default loadout.

Limits: a save during a cutscene keeps no script state. Actors come back at their squad starts, as after a death revert (not where they stood). A revert after Continue at a checkpoint clears the overshield and camouflage, as any revert does; Continue at a section's start makes the carried script the state a death before the first checkpoint reverts to, where a live session restarts the script on that section (an existing in-memory limit). Re-importing the scripts (`import_halo_scripts.py`) changes the `.hscb` hash, so saves made before it continue with the script restarted. The file keeps only the checkpoint's loadout, so Restart section after a Continue at a checkpoint starts the section with that loadout, not the one the player first brought into it. Under the title menu at launch the stock level the engine boots into keeps running.

## Nav points and HUD script commands

**Not verified in the game yet**: written and compiled while testing was on hold. `tests/test_nav_points.py` is written but has not been run.

The mission scripts' nav point commands are bound: `activate_team_nav_point_flag <type> <team> <flag> <offset>` and `activate_team_nav_point_object <type> <team> <object> <offset>`, the per-unit `activate_nav_point_flag` and `activate_nav_point_object`, and the four matching `deactivate_*` commands (single player: the team or unit is not checked). A point is a cutscene flag or an object (it follows the object), raised by the offset in Halo world units; activating the same flag or object again replaces it. Nav points are saved with each checkpoint and restored by a revert, carried across sections within a mission and cleared when the mission script starts afresh. `source/src/halo_hud.cpp` draws them with the retail waypoint arrows: `tools/halo_hud.py` now exports the HUD globals' `hud_waypoints` bitmap and its ten arrow types (name, colour, opacity, on-screen, off-screen and occluded sequences) as `waypoint` and `arrow` lines in `packages/halo/hud.txt` (re-run `python3 tools/halo_hud.py "$maps"`; the bitmap ids of the other sheets shift, and the exporter now compares page contents so the copied textures follow). A point on screen gets the type's on-screen marker in its colour (blue for `default`, red for `default_red`); a point off screen or behind the view gets the off-screen arrow on the screen's edge, turned towards it. Occlusion is not tested, so the occluded sequence is not used. Without those lines the points are drawn as diamonds and edge triangles. While any nav point is active, the engine's own route diamond is hidden.

`hud_show_health`, `hud_show_shield`, `hud_show_motion_sensor` and `hud_show_crosshair` hide and show those parts of the retail HUD (and of the fallback HUD), and `hud_blink_health`, `hud_blink_shield` and `hud_blink_motion_sensor` flash them, as a10's cryo tutorial does on Normal (it hides the health, shield, motion sensor and reticle and reveals each in its lesson). The state is saved with checkpoints and reset when the mission script starts afresh. `hud_set_objective_text`, `hud_set_help_text` and `show_hud_help_text` were already bound. `show_hud` (the chapter title scripts) and `display_scenario_help` stay no-ops.

The retail reticles now hang from their registration point measured from the sprite's own corner (as the exported sheets store it), not from the page's; reticles on combined sheets whose sprite is not in the page's top-left corner were drawn off centre before. Also unverified in the game.
